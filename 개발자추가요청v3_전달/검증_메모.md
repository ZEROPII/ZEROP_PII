## 1. 기존 코드·로그 분석 (수정 전)

### A. 응답 시간
- **turn 0 `sec_answer` 누락 원인**: 턴 0의 대상 AI 호출·원 응답 추출은 `ArmRun`이 아니라 `make_prefix`(갈래 간 공유)에서 실행된다. `_turn`은 `raw`를 받아서 들어오므로 `t_target`이 None이 되고, 패치 코드가 `turn >= 1 and t_target is not None`일 때만 값을 넣었다. 기존 로그: 턴 0 60행 모두 None.
- **기존 계산**: `sec_target = t_target − t_begin`, `sec_extract = t_extract − t_target`, `sec_release = t_release − t_extract`. 시계는 `time.perf_counter`, 기록 위치는 `턴기록.jsonl`.
- **C0 정의 불일치**: 기존 패치의 C0 `sec_answer`는 `t_target − t_begin`(대상 AI만)이었다. 요청서 정의(target + release)와 다르다. 추출 시간은 포함되지 않았다.
- **TTFT**: 기록된 적 없음. `core/llm_client.py`는 `requests.post`로 비스트리밍 호출하므로 첫 토큰 시각을 관측할 수 없다.
- `llm_usage.jsonl`의 `latency_ms`는 HTTP 왕복(마지막 성공 요청만), `sec_*`는 벽시계 경과(재시도 대기·throttle 포함)라 서로 다르다.

### B. 추출 실패
- **`REFUSAL_EXTRACTION_FAILED` 조건**: C1·C1S에서 원 응답 추출 `extract()`가 `max_extract_retries + 1 = 3`회 모두 `parse_json(..., "array")` 실패 → `release()`가 거절문을 공개한다 (`session.py` `release`). C0는 같은 실패가 있어도 원문을 공개하고, 측정만 빠진다.
- **잘림 원인**: extractor `max_tokens=2048`. 추출 출력이 관찰마다 긴 JSON 객체라 상한에 걸린다 (평균 1,583, P50부터 2,048).
- **파싱 처리**: `tracking.parse_json`은 전체 파싱 → 실패 시 `[`마다 `raw_decode` 시도. 잘린 배열은 닫히지 않아 실패한다.
- **재시도 기록**: 시도 수(`extraction_tries`)만 있고 시도별 결과·잘림 여부는 없었다.
- **연결 가능성**: 기존 `llm_usage.jsonl`에는 trial·턴 키가 없다. 순차 실행이라 코드 경로대로 역할 순서를 재구성했고 914/914행이 일치했다 (`출력토큰_분석.md` §3). 이 범위에서 34건을 호출에 연결했다. 단, 이것은 **기록된 키가 아니라 순서 재구성**이다. verify(공개 확인) 추출은 시도별 성공 여부를 기록에서 알 수 없어 분류하지 않았다.
- **결과**: 34건 모두 3회 시도 × 3회 잘림 (턴 0: 24, 턴 ≥1: 10). 원 응답 추출 실패 시도 156건이 모두 잘림이었다. 잘림 없는 JSON 오류는 0건.
- **추가 관찰**: NO_CASE 51 trial 중 48개(C0 24 + C1 24)는 턴 0 추출 실패 때문이다. 턴 0 추출이 실패하면 사례가 하나도 등록되지 않아 trial이 바로 끝난다. 기존 실행의 위반율은 대부분 측정되지 않은 trial로 이루어져 있다.

### C. 실험 대상 선정
- `plan_trials`: 질문 유형 3 × 역할 2 = 6칸, 칸마다 `trials_per_cell`명(기본 2)을 비복원 추출 → 기본 12명. `--limit`은 이 목록을 **자르기만** 하고 늘리지 않는다.
- 그래서 `--limit 30`만 주면 12 trial, `--trials-per-cell 5`를 주면 30 trial이다. 설계대로의 동작이다 (버그 아님).
- `--budget 12`는 trial당 턴 수 상한이고 trial 수와 관계없다. 요청서 §2-3 명령에는 `--trials-per-cell 5`가 빠져 있어 그대로 실행하면 12명만 나온다.
- 지난 실행(run_20261107_151400)은 `arms=C0,C1`이었다 (C1S 없음).

## 5. 정의 요약 (보고서에 쓰는 기준)

- **유효 출력 비율**: 턴(턴 0 포함) 중 원 응답 추출이 파싱된 비율. 갈래별.
- **세 처리 (trial 단위, 사례 A Validated 위반)**: 분모 N = 갈래 trial 수 (LLM_ERROR 제외, 따로 표시). 영향 trial = 원 응답 추출 실패 턴이 하나 이상. 배포 규칙 = 관측 그대로. 최선 = 영향 trial 결과를 결측으로 보고 모두 위반 없음. 최악 = 영향 trial을 모두 위반 있음. 완전 사례율은 참고. 이 처리 규칙은 표준이 아니라 설계 선택이다.
- **추출 실패 원인**: 잘림 + 파싱 실패 → `TRUNCATED`(동반 `JSON_PARSE_ERROR`), 잘림 없이 파싱 실패 → `JSON_PARSE_ERROR`, 잘림 여부 미상 → `OTHER`. 블록(1~3회) 단위 주 원인은 마지막 시도의 원인이고, 시도별 원인을 함께 남긴다.
- **지연**: P50·P90·P95·P99(참고)·IQR, 선형 보간. 95% CI는 질의 환자 단위 부트스트랩(B=2000, 시드 20261107). 관측값 있는 환자가 2명 미만이면 CI를 만들지 않는다.

## 6. TTFT — 측정 불가 사유와 향후 변경

- 사유: `core/llm_client.LLMClient._send_with_retry`가 `requests.post(json=payload)`로 전체 응답을 한 번에 받는다. 첫 토큰 도착 시각이 없다.
- 기록: 턴마다 `sec_ttft = null`, `ttft_status = "NOT_OBSERVABLE_NON_STREAMING"`. usage 행 `ttft_ms = null`. 전체 응답 시간을 TTFT로 쓰지 않는다.
- 향후 필요한 변경: (1) payload에 `"stream": true`, `requests.post(..., stream=True)`로 SSE를 읽고 첫 `content_block_delta`(text) 시각을 기록, 사용량은 `message_delta`의 usage에서 읽기 (2) `LLMResponse`에 `ttft_ms` 필드 (3) 배포 경로 TTFT 정의 결정: C0 = 대상 AI 첫 토큰, C1·C1S = 추출·방어가 끝나야 공개되므로 "공개 답 첫 바이트"(현재 구조에서는 sec_answer와 거의 같음). 프록시(monogpt)가 스트리밍을 지원하는지도 확인해야 한다.

## 7. 검토 필요 사항 (임의로 결정하지 않음)

1. **target max_tokens 1200 (잘림 44.7%)** — 실험 조건이라 유지. 바꿀지, 잘린 답변을 별도 표로만 보고할지 결정 필요.
2. **extractor 2560이 충분한지** — 기존 분포가 상한에서 검열되어 있어 근거가 하한이다. 본 실험 후 `token_usage_summary.md`의 extractor 잘림 비율과 `extraction_summary.md` 원인표를 확인하고, 여전히 TRUNCATED가 주 원인이면 새 분포로 다시 계산.
3. **온도 0 재시도** — 같은 입력이라 같은 잘림이 반복된다. 재시도 정책 변경은 판정 기준 변경이라 손대지 않았다.
4. **잘렸지만 파싱된 추출** — `parse_json`은 `[]`(빈 배열)도 성공으로 받으므로, 잘린 출력 안의 빈 배열 조각이 "관찰 없음"으로 파싱될 가능성이 이론상 있다. 기존 로그에서는 0건. 진단표의 "잘렸지만 파싱된 시도"로 감시한다.
5. 브랜치 변경(`feat/medical-integration` → `turn_Time_chekcer`)이 의도한 것인지 확인.

## 8. 본 실험 실행 명령 (사용자 직접 실행)

PowerShell, 저장소 루트에서. 출력 폴더가 이미 있으면 코드가 중단하므로 기존 결과는 덮어쓰지 않는다.

```powershell
# 1) 배선 확인 (토큰 0)
python -m medical run --dry-run --arms C0,C1S,C1 --limit 30 --trials-per-cell 5 --mode exploration --budget 12 --model claude-haiku-4-5-20251001 --out runs/medical/dryrun_A2_check

# 2) 본 실험 (실제 API)
python -m medical run --arms C0,C1S,C1 --limit 30 --trials-per-cell 5 --mode exploration --budget 12 --model claude-haiku-4-5-20251001 --out runs/medical/A2_C0_C1S_C1

# 3) 집계 (LLM 0) — run 명령 끝에서도 자동 생성됨
python -m medical report runs/medical/A2_C0_C1S_C1
```

- `--trials-per-cell 5`가 없으면 12 trial만 실행된다.
- 실행 후 확인: `run_meta.json`의 `trial_selection.selected = 30`, `git_commit`, `git_dirty`(커밋하지 않고 실행하면 true와 diff 해시가 남음).
- 호출량 주의: 기존 실행은 턴 0 추출 실패로 trial 대부분이 즉시 끝나 914호출이었다. 같은 조건의 dry-run은 5,288호출이었다. 추출이 정상화되면 실제 호출 수는 수천 건으로 늘 수 있다 (Mock 기준 추정이며 실제 값이 아님).

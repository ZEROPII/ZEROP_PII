# ZEROOP2 개발 진행 현황

> **기준일:** 2026-10-27  
> **단계:** Clinical Case Finder 프론트엔드 구현 및 실제 의료 연구 파이프라인 1차 연동 완료 / 연구 모듈 결함 분석·검증 대기  
> **근거:** Claude Code 작업 완료 보고 및 테스트 결과. 본 문서는 소스코드·로그를 직접 재검증한 결과가 아닌 **보고된 구현 현황**을 정리한 문서입니다.

## 1. 프로젝트 개요

ZEROOP2는 의료 데이터 기반 대화형 AI에서 개인정보(QI, 준식별자)의 누적 공개로 발생할 수 있는 재식별 위험을 분석하고, **누적 State·k 계산·Defender 정책**을 통해 공개 답변을 제어하는 연구 프로젝트입니다.

이번 개발 범위는 기존 `medical/` 연구 파이프라인을 변경하지 않고, 이를 의료 유사 사례 조회 인터페이스인 **Clinical Case Finder**에서 호출할 수 있도록 프론트엔드와 HTTP API 계층을 구축하는 것입니다.

**현재 결론:** 화면 구현과 API 연결은 이루어졌으며, 실제 LLM 호출·QI 추출·Defender·State·k 계산을 연결한 동작도 일부 확인했습니다. 그러나 **QI 추출 출력 잘림과 날짜 정규화 누락**이 발견되었고, 실제 HTTP 모드에서의 브라우저 전체 검증 및 연구 정확도 재검증은 남아 있습니다. 운영 가능한 의료 서비스로 검증된 상태는 아닙니다.

## 3. 시스템 구조

```text
[Clinical Case Finder / frontend/]
        |  사용자 질문, 사례 선택
        v
[FastAPI / api_server/]
        |  기존 연구 모듈 호출
        v
[medical/ 연구 파이프라인]
        |  원 응답 생성 (대상 LLM)
        |  QI 추출
        |  Defender 판정: allow / generalize / suppress
        |  필요 시 응답 재작성 및 재추출 확인
        |  최종 공개 정보만 사례별 누적 State에 반영
        |  kcalc 기반 k 계산
        v
[공개 허용 응답 + 위험 상태 + 공개 이력]
        |
        v
[프론트엔드 표시]
```

**설계 원칙**

- 원 응답과 최종 공개 답변을 구분합니다. 프론트엔드에는 보호 정책에 따라 공개된 결과를 전달합니다.
- k는 프론트엔드에서 계산하지 않습니다. 실제 모드에서는 기존 `medical/` 연구 모듈의 결과를 표시합니다.
- 연구 하네스처럼 **대화 흐름은 하나이고 State는 사례별로 누적**합니다. 답변에 여러 사례의 정보가 포함되면 `relatedRiskStates`로 관련 사례의 상태를 함께 갱신합니다.
- 원 응답·검색 문서 본문·환자 ID·문서 ID는 API 응답에 포함하지 않고 서버 측 `runs/api/`에 기록하도록 구현했다고 보고되었습니다. **서버 기록 자체의 접근 통제 및 보관 정책은 추가 점검이 필요합니다.**
- 기존 `medical/` 연구 모듈은 이번 연동 과정에서 수정하지 않았다고 보고되었습니다.

## 4. 구현된 기능

### 4.1 프론트엔드 (`frontend/`)

- **현재 환자 맥락 / 유사 사례 목록:** 환자 정보와 검색 사례를 분리하여 표현합니다. 실제 모드에서는 Defender를 거치지 않은 사례 진단명을 목록에서 노출하지 않고 검색 순위·유사도만 제공합니다.
- **AI 대화:** 질문 입력, Enter 전송, Shift+Enter 줄바꿈, 한글 조합 중 오전송 방지, 응답 로딩·오류·재시도 UI를 지원합니다.
- **개인정보 보호 결과:** 일반화된 문구 강조, 비공개 처리 내역, 판정 근거 모달, 턴별 공개 이력을 표시합니다.
- **위험 시각화:** 사례별 누적 k 및 Defender가 반환한 위험·공개 허용 상태를 표시합니다. 프론트엔드가 k만으로 정책을 재판정하지 않습니다.
- **사례 전환:** 사례별 대화·상태·입력 내용을 유지합니다. 화면 폭 390px에서는 3개 영역이 탭으로 전환됩니다.
- **조회 기록·보호 정책 화면:** 별도 페이지로 구현되었습니다.
- **실행 모드:** 기본 Mock 모드와 실제 API를 호출하는 HTTP 모드를 지원합니다. Mock 및 dry-run은 실제 연구 결과와 구분되는 표시를 둡니다.

주요 프론트엔드 구성:

```text
frontend/src/
├── types/domain.ts       # 도메인 타입과 상태 필드
├── api/types.ts          # 프론트엔드 API 계약
├── api/httpApi.ts        # 실제 HTTP API 호출
├── api/mock/             # Mock 데이터·서비스
├── state/                # 화면 상태 및 사례별 데이터 관리
├── components/           # 재사용 UI 구성요소
└── pages/                # 화면별 페이지
```

### 4.2 API 서버 (`api_server/`)

- FastAPI 기반 HTTP API 서버를 새로 구현했습니다.
- 기존 `frontend/src/api/types.ts` 및 `httpApi.ts`의 계약과 기존 10개 API 경로를 유지했다고 보고되었습니다.
- API 접두사는 `/api`이며, 상태 확인과 세션 초기화를 위한 `/health`, `/session/reset` 엔드포인트가 추가되었습니다. **정확한 전체 URL·요청/응답 스키마는 `api_server/README.md`를 기준으로 확인**합니다.
- 연구 호출은 기존 `ArmRun._turn`을 사용합니다. 세션 준비는 `plan_trials`, `query_binding`, `retrieve`를 사용합니다.
- 질문에 사례 표기가 없다면 LLM으로 전달하는 질문에만 사례 맥락을 붙이며, 화면에는 사용자가 작성한 원문을 유지합니다.
- 예외 처리: 없는 사례 `404`, 세션 불일치 `409`, 빈 질문 `422`, LLM 호출 실패 `502`(이때 State 유지). 오류 본문에는 의료 원본 데이터를 포함하지 않습니다.
- `C0`, `C1`, `C1S` 실행 갈래를 기존 하네스에 맞춰 사용합니다. **C0는 원 응답 공개 실험 모드이므로 실제 환자 데이터가 있는 일반 서비스로 노출해서는 안 됩니다.**

### 4.3 기존 연구 모듈 연동

- QI 추출기: 기존 의료 연구 모듈의 **QI 8종 추출기** 연결.
- 누적 State: `Case.committed` 기반으로 공개 결과 누적.
- k 값: `kcalc`의 사건 단위 계산 결과 사용.
- 개인정보 보호: `MedicalDefender`의 `allow`·`generalize`·`suppress` 적용.
- 공개 검증: 필요한 경우 재작성하고 재추출하여 공개 가능한 답변을 결정.
- 정책 설정: `medical/config.py`의 기존 설정(**generalize = 5, suppress = 3**) 사용. 이 값의 정책적 의미는 연구 코드 정의에 따르며, 프론트엔드의 임의 기준으로 대체하지 않습니다.

## 5. 실행 방법

### 5.1 백엔드 — 프로젝트 최상위 폴더

```powershell
# 실제 LLM 호출, 기본 C1
python -m api_server

# 가짜 LLM 기반 개발 모드 (토큰 사용 0, 수치에 연구적 의미 없음)
python -m api_server --dry-run

# C1S 실행, 시험 trial 지정
python -m api_server --arm C1S --trial T0003
```

실제 LLM 실행을 위해서는 저장소와 `api_server/README.md`가 요구하는 환경 변수·인증 설정이 준비되어 있어야 합니다. 여기서는 확인되지 않은 API 키 이름이나 포트를 임의로 기재하지 않습니다.

### 5.2 프론트엔드 — 별도 터미널

```powershell
cd frontend
npm install

# 기본: Mock 모드
npm run dev
```

실제 HTTP 모드로 실행하려면 **PowerShell**에서 다음과 같이 환경 변수를 설정합니다.

```powershell
cd frontend
$env:VITE_API_MODE = 'http'
$env:VITE_API_BASE_URL = '/api'
npm run dev
```

기본 Vite 개발 서버 주소는 보통 **http://localhost:5173/** 입니다(실제 터미널 출력 우선). 개발 중 `/api` 요청은 `vite.config.ts`의 프록시를 이용해 백엔드로 전달합니다. 서버 주소가 다를 경우 프록시 설정을 함께 확인해야 합니다.

모드별 차이:

| 모드 | 데이터·응답 | k 및 정책 결과 | 목적 |
|---|---|---|---|
| Mock | 브라우저 Mock Service | 사전 정의한 예시 값 | UI 시연·컴포넌트 테스트 |
| HTTP + dry-run | 백엔드, 가짜 LLM | **숫자 의미 없음** 표시 | 통신·흐름 검증 |
| HTTP + 실제 LLM | 백엔드, 기존 연구 파이프라인 | 실제 모듈 계산 결과 | 연구 연동 및 오류 분석 |

## 6. 현재까지 보고된 테스트 결과

| 테스트 | 결과 | 해석 |
|---|---|---|
| 초기 프론트엔드 | 11건 통과 | Mock UI 기능 확인 당시 결과 |
| 연동 후 프론트엔드 | **12건 통과** | 타입 검사 및 빌드도 통과 |
| `tests/api_server` | **8건 통과** | 가짜 LLM으로 API·상태·보호 결과 검증 |
| 기존 전체 pytest | **209건 통과, 1건 실패** | `test_bundle_code_is_unchanged` 해시 불일치. Claude 보고상 `core.autocrlf=true`/CRLF 원인으로, 독립 재확인 필요 |
| 실제 LLM + HTTP | 질문 **4개** 실행 | 대상 AI·추출기·재작성기 호출 확인, 아래 결함 발견 |
| 실제 HTTP 모드 브라우저 E2E | **미실시** | API 응답과 TypeScript 계약 일치까지만 확인 |

실제 LLM 테스트 중 처방 관련 응답에서 **1건 비공개, 2건 그대로 공개**, k **461 → 52** 갱신이 보고되었습니다. 다른 사례의 k는 **461**로 유지되었다고 합니다. 이는 연동 예시이며 전체 알고리즘의 보호 정확도나 안정성을 입증하는 수치는 아닙니다.

## 7. 발견된 문제와 연구 영향

### [P0] 날짜/기간 `PERIOD`가 누적 State와 k 계산에서 누락될 가능성

- 재현 보고: `2018년 3월 9일부터 …`와 같은 표현을 추출기가 `PERIOD`로 반환했으나, 정규화 계층(`normalize_bridge`)에서 `UNMAPPED`로 처리되었습니다.
- 영향: **최종 공개된 날짜 정보가 State와 kcalc에 반영되지 않으면 후보 수 k가 실제보다 크게 평가되어 재식별 위험이 과소평가될 수 있습니다.**
- 확인 사항: 날짜가 정식 QI 평가 대상인지, `PERIOD`의 의미와 정규화 규칙, kcalc 지원 범위, Defender가 `UNMAPPED` 표현을 최종 공개할 수 있는지.
- 임시 원칙: 원인 및 안전성이 확인될 때까지 **미매핑 날짜성 표현을 안전하다고 취급하지 않도록** 검토해야 합니다. 코드 수정 전에는 재현 테스트와 영향 분석을 우선합니다.

### [P1] QI 추출기 출력이 `MAX_TOKENS=2048`에서 잘림

- 재현 보고: 실제 질문 4개 중 2개에서 추출기 출력 잘림(`truncated=True`)이 관찰되었고, 3회 재시도에도 JSON 파싱이 실패했습니다.
- 현재 동작: fail-closed로 답변을 거절합니다. 이는 무분별한 공개를 피하지만 정상 요청 처리율을 저하시킬 수 있습니다.
- 확인 사항: 실제 종료 사유, 출력 토큰 길이, 프롬프트와 JSON 구조, 재시도 로직.
- 수정 방향: 출력 길이 설정 및 응답 형식 개선을 **기준선과 분리된 실험**으로 비교합니다. 기존 연구 설정을 무단 변경하지 않습니다.

### [P1] 실제 UI·세션·로그의 추가 검증 필요

- HTTP 모드에서 **브라우저 조작을 포함하는 End-to-End 테스트**가 아직 수행되지 않았습니다.
- 사례별 State 분리 검증과 별개로 **서로 다른 사용자/HTTP 세션 간 상태 격리 및 동시 요청**을 확인해야 합니다.
- `runs/api/`에 남는 원 응답·검색 본문의 **접근 통제, 보관 기간, Git 무시 처리**를 점검해야 합니다.
- 기존 해시 테스트 1건의 CRLF 원인은 보고된 추정이므로 원인 재검증이 필요합니다.

## 10. Git 상태 및 범위 유의사항

- 보고 시점 프론트엔드·API 서버 작업은 **아직 커밋되지 않았습니다.**
- Claude Code는 작업 중 `git stash` 복원 충돌을 겪었으나 작업 변경을 복원했으며, 기존 GitHub Desktop 스태시 2개도 보존되었다고 보고했습니다. 작업 내용을 신뢰하기 전에 `git status`, `git diff`, `git stash list`로 재확인하세요.
- 기존 연구 모듈은 변경하지 않았다고 보고되었으나, 커밋 이전에는 변경 파일 목록을 확인하는 것이 안전합니다.
- 본 문서의 **완료**는 구현·연동 및 보고된 테스트 범위를 뜻하며, 임상 사용 승인, 개인정보 비식별화 보장 또는 전체 연구 실험의 타당성 검증을 뜻하지 않습니다.

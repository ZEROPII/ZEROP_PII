# ADR-0020. 의료진 화면은 EMR 진료 지원 AI로 두고 위험 분석은 보안 담당자 화면으로 옮긴다

## 배경

11월 3일 통합 화면의 의료진 화면에는 후보 수(k), 후보 렌즈, 사례별 위험 막대, 판정 근거와 "그대로 답하면 사례 1 후보가 6명에서 1명으로 줄어듭니다" 같은 보내기 전 숫자가 그대로 보였다. 11월 4일 화면 검토에서 "의료진이 쓰는 LLM 화면에 위험도 분석이 보이는 것이 맞는가, 병원 EMR에 들어간 LLM 화면과 동떨어진다"는 문제가 나왔다.

또 보안 담당자의 '의료진에게 확인 요청'은 감사 기록에만 남고 의료진 화면에는 도착하지 않았다(사람 검토 시나리오 점검에서 확인). 사람이 판단하는 단계가 화면 안에서 끝나지 않았다.

## 결정

- 의료진 화면(`/`, `/history`, `/guide`)은 병원 EMR 안의 진료 지원 AI 형태로 둔다: 앱 머리줄, 진료 중 환자 띠, 비슷한 사례 | 대화 | 사례 노트. 화면 토큰은 `[data-app='emr']`(청록 계열)로 보안 담당자 화면(남색)과 나눈다.
- 의료진 화면에는 재식별 위험 숫자(후보 수, 기준값)를 보이지 않는다. 가린 값은 '비공개', 넓힌 값은 '범위'로만 표시하고, '왜 그런가요?'에서 숫자 없이 이유를 설명한다. 문구는 `frontend/src/lib/clinicianCopy.ts`에서만 만든다.
- 보내기 전 확인은 후보 수 대신 보내면 어떻게 보이는지만 알린다. 데모 서버 preflight가 `plannedAction`(suppress · generalize)과 질문이 가리킨 사례(`targetCaseLabel`)를 함께 보낸다.
- 위험 분석은 보안 담당자 화면으로 옮긴다. 새 '의료진 대화'(`/watch`) 화면에 후보 렌즈, 사례별 후보 수, 숫자가 붙은 대화, 나간 정보와 판정 근거, 질문 미리 세기(상태를 바꾸지 않음), 단서 그래프를 모은다. 보호 정책(기준 5 · 3)도 보안 담당자 메뉴로 옮기고, 의료진에게는 숫자 없는 '보호 안내'를 둔다.
- 의료진과 보안 담당자가 메시지를 주고받는다(`Session.messages`). 의료진은 세부 정보 요청 · 답장, 보안 담당자는 답장 · 확인 요청을 보낸다. 확인 요청은 검토 표시(ask_clinician)와 함께 남고 의료진 화면 대화 위에 뜬다. 마지막 메시지를 의료진이 보냈으면 관제 목록 맨 위로 올린다. 메시지는 모두 감사 기록에 남는다.
- 사례 노트는 옵시디언 노트 방식으로 만든다: 속성(진단 · 약 · 시술 값은 용어 사전 [[링크]]), 연결된 질문(누르면 대화의 그 질문으로), 같은 값이 나온 사례. 공개 이력의 턴과 질문을 잇기 위해 데모 서버와 api_server가 대화 메시지에 `engineTurn`(대화 전체 턴 번호)을 붙인다.
- 단서 그래프(옵시디언 그래프 보기 방식)는 보안 담당자 화면에만 둔다. 여러 사례에 공통인 값은 가운데로, 한 사례에만 붙은 값은 그 사례 둘레에 남는다.
- 제품 이름은 MediCloak으로 쓴다. 의료진 화면에서는 머리줄의 'MediCloak 보호 적용' 표시로만 드러낸다.

## 근거

- 의료진에게 필요한 것은 진료 판단에 쓸 내용과, 값이 왜 빠졌는지에 대한 짧은 설명이다. 후보 수는 보안 담당자가 판정을 검토할 때 쓰는 숫자다.
- 보내기 전에 "몇 명까지 줄어드는지"를 보여 주면, 숫자가 기준을 넘을 때까지 질문을 바꿔 보는 데 쓰일 수 있다. '비공개' · '범위'만 알리면 그런 피드백이 없다.
- 확인 요청이 의료진에게 도착하고 답장이 돌아와야 사람 검토 단계가 실제로 닫힌다.
- 공개 이력과 대화 기록만으로 노트를 만들면 백엔드에 새 계산을 더하지 않아도 된다.

## 검토한 대안

- 보안 담당자가 승인하면 가린 원래 값을 의료진에게 보내기: 후보가 1명으로 줄어드는 값을 내보내면 방어가 무력해진다. 이번에는 넣지 않고, 답장으로 처리 결과와 대안을 알린다.
- 의료진 화면 API에서도 후보 수를 지금 바로 빼기: 보안 담당자 '의료진 대화' 화면이 같은 API와 화면 상태를 쓰고 있어, 역할별 응답을 나누려면 API 클라이언트와 상태를 둘로 나눠야 한다. 이번 범위에서는 화면에서만 숨기고 남은 일로 둔다.

## 결과와 영향

- 데모 순서가 바뀐다: 의료진 화면에서 묻고 답을 본 뒤, 보안 담당자 '의료진 대화'에서 같은 대화를 숫자와 함께 본다. 세부 정보 요청 → 관제 답장 → 의료진 메시지 도착까지 한 화면 전환 안에서 보여 줄 수 있다.
- 의료진 화면 문구에 숫자가 들어가지 않는지 테스트로 확인한다(`frontend/src/lib/clinicianView.test.ts`). 프런트 테스트 36개, 데모 서버 테스트 14개(메시지 흐름 · plannedAction 2개 추가), api_server 테스트 1개(engineTurn · value) 추가.
- 쓰지 않게 된 통합 화면 부품(CaseFinderPage, ChatPanel, PreflightWarning, PatientContextCard, CaseList)은 지웠다. 기능은 위 두 화면으로 나눠 옮겼다.
- 두 화면은 역할에 따라 틀(앱 머리줄)부터 다르므로, 역할은 그리는 시점에 주소로 정한다. 화면 안에서 역할을 바꿀 때 이전 역할의 틀이 한 번 그려지면 의료진 화면 부품이 메시지 제공자 밖에 놓여 화면이 비었다(코드 검토에서 발견, 같은 날 수정).

## 남은 일

- 의료진 화면 API(`/api/cases/…`, `/api/risk-states`, `/api/cases/{id}/disclosures`)는 아직 후보 수와 숫자가 든 설명을 담아 보낸다. 화면에서만 숨긴 상태이므로, 역할별로 응답을 나누는 서버 쪽 분리가 필요하다. 양승준.
- 실제 LLM 서버(api_server)에는 메시지 경로가 없어, 그 서버에 붙이면 세부 정보 요청 버튼이 숨겨진다.

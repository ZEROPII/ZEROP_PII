# ADR-0030. 보안 담당자 화면을 고친다

## 배경

2026-11-06 의료진 · 보안 담당자 계정으로 운영 모드를 함께 써 본 통합 체험 기록에서, 보안 담당자 쪽은 다음이 걸렸다. 코드에서 확인한 그때의 동작을 함께 적는다.

- **원문 열람 사유가 미리 골라져 있었다.** 열람 창을 열면 '오탐 확인'이 골라져 있어 누르기만 하면 열렸다. 무엇을 보려는지는 남지 않았다.
- **감사 기록에 누구의 정보를 다뤘는지가 없었다.** 열람 · 승인 · 규칙 · 질문 기록에 대화 번호(T0014 같은 질의 번호)만 있고, 지금 환자와 찾은 사례(과거 환자)가 누구였는지 이어 볼 수 없었다.
- **기준 아래로 내려가는 공개도 사유 5자로 승인됐다.** 승인 창은 값마다 '그대로면 N명'만 보였고, 고른 값을 함께 공개한 뒤의 후보 수는 승인한 뒤에야 알 수 있었다.
- **승인 공개가 경보로 셌다.** 보안 담당자가 승인해 후보가 기준 아래로 내려간 사례가 '기준 아래로 내려간 사례가 N건 있습니다. 바로 확인하세요'로 떴다. 스스로 승인한 일이 경보가 되어 방어 규칙이 놓친 경우와 구별되지 않았다.
- **요청이 온 대화를 열면 요청한 사례가 아닌 다른 사례가 먼저 보였다.** 초점이 '그대로면 후보가 가장 적은 사례'로 정해졌다.
- **같은 요청 · 답장이 두 번 들어갔다.** 단추를 빨리 두 번 누르면 메시지와 감사 기록이 두 줄씩 남았다.
- **걸지 못한 규칙은 기록이 없었다.** 의료진이 이미 다른 환자로 옮긴 대화 등에 규칙을 걸다 실패하면 아무것도 남지 않았다.
- **감사 기록 화면 문구**: 서버 종류를 알기 전 잠깐 동안 운영 서버에서도 '서버를 다시 켜면 지워지는 데모 기록입니다'가 보였다.
- **상세 화면이 숫자 · 막대부터 보였다.** 무엇이 위험했고 지금 무엇을 해야 하는지보다 세 갈래 비교 막대와 후보가 줄어든 과정이 먼저 보였다.
- **대화를 나눠 물으면 보이지 않았다.** 누적 판정은 대화마다 따로 센다. 같은 과거 환자를 다른 대화 · 다른 의료진이 나눠 물어도 화면에 아무 표시가 없었다.

체험 기록의 제안 가운데 두 가지는 이번에 하지 않는다(사용자 결정).

- 기준 아래로 내려가는 승인에 **2인 확인**(두 번째 보안 담당자 계정)을 두는 것. 계정을 하나 더 만들어야 한다.
- 상태 이름 '▲ 특정 시도 막음'을 바꾸는 것. 지금 이름과 색을 그대로 둔다.

## 결정

판정 · 후보 수 · 판정 규칙 판(v5)은 바꾸지 않는다. 보안 담당자 화면과 감사 기록만 바꾼다.

### 1. 원문 열람: 사유를 고르고 한 줄을 적어야 열린다

- 열람 창에 미리 골라 둔 사유가 없다. 사유(오탐 확인 · 의료진 문의 대응 · 규칙 수정 검토 · 기타)를 고르고 '확인하려는 것'을 5자 이상 적어야 '기록 남기고 보기'가 눌린다.
- 운영 모드 서버는 `note`가 5자 미만이면 422로 막는다(`POST /api/monitor/sessions/{sid}/reveal`). 데모 서버는 화면만 막는다.
- 감사 기록 `reveal`에 사유와 적은 내용, 열람으로 보이게 되는 모든 환자의 기호가 남는다.

### 2. 감사 기록에 환자 기호

- 기호: `"P-" + HMAC-SHA256(키, 환자 번호 앞 8자)` 앞 6자(`Monitor.tag`). 같은 번호는 늘 같은 기호이고, 키 없이는 기호에서 번호를 알 수 없다.
- 키는 처음 쓸 때 만들어 DB meta `subject_tag_key`에 둔다. 서버를 다시 켜도 같은 기호다. DB가 없는 데모 서버는 켤 때마다 새 키를 쓴다.
- 감사 기록에 `patient_tag`(지금 환자) · `subjects`([{case, tag}], 다룬 사례)를 남긴다: 원문 열람 · 확인 요청 · 규칙 걸기/풀기/실패 · 공개 승인 · 의료진 메시지 · 의료진 질문 · 새 대화 · EMR 열기 · 첫 답 미리 준비.
- 관제 상세에는 번호 대신 기호가 늘 보인다(지금 환자 · 초점 사례). 번호는 지금처럼 열람한 뒤에만 보인다.

### 3. 기준 아래로 내려가는 공개는 고위험 승인 (2인 확인 대신)

- 승인 창은 값을 고를 때마다 서버에 함께 공개한 뒤의 후보 수를 묻는다(`POST /api/monitor/sessions/{sid}/what-if`, 승인과 같은 계산, State는 바꾸지 않음).
- 가장 적은 후보 수가 기준(5명) 아래면:
  - 빨간 칸에 몇 명까지 줄어드는지 보이고, '후보가 N명까지 줄어드는 것을 알고 공개합니다' 확인란을 받는다. 고른 값이 바뀌면 확인란은 다시 비운다.
  - 사유는 15자 이상(`HIGH_RISK_REASON`). 보통 승인은 지금처럼 5자.
  - 서버도 같은 조건을 다시 센다. `confirmLowK`가 없거나 사유가 짧으면 422.
- 승인 기록과 감사 기록 `approve_release`에 `high_risk`와 공개 뒤 가장 적은 후보 수(`k_min`)를 남긴다. 화면에 '고위험' 표시가 붙는다.

### 4. 승인 공개로 내려간 사례는 경보와 따로 센다

- 방어 규칙이 지킨 후보 수는 첫 승인 공개 전까지의 턴 기록으로 센다. 그때 기준 이상이었고 승인한 값 때문에 기준 아래가 된 사례는 `approved_low`, 나머지 기준 아래 사례는 `violated`(경보)다.
- 관제 첫 화면의 '기준 5명 아래 사례'(`kpi.identified`)는 `violated`만 센다. '승인 공개로 기준 아래'를 따로 보인다. 목록 줄에도 '기준 아래 · 사례 N'(빨강)과 '승인 공개로 기준 아래 · 사례 N'(회색)을 나눠 적는다.

### 5. 요청이 온 대화는 요청한 사례부터

- 보안 담당자가 답할 차례인 요청이 있으면 그 요청의 사례가 초점이다(목록의 후보 수 · 상세의 후보 수 칸 · 세 줄 요약).

### 6. 두 번 보내기를 한 번으로

- 대화의 마지막 메시지와 보낸 쪽(의료진 · 보안 담당자) · 종류 · 사례 · 글이 같고 15초(`DUP_WINDOW`) 안이면, 새로 쓰지 않고 앞의 것을 돌려준다(`Monitor._duplicate`). 의료진 요청 · 답장, 보안 담당자 답장 · 확인 요청이 해당된다. 감사 기록도 한 줄이다.

### 7. 걸지 못한 규칙도 감사 기록에

- 규칙 걸기가 실패하면(409 · 422) `add_rule_failed`에 사례 · 단서 · 메모 · 까닭(`why`) · 환자 기호를 남긴다. 화면에는 '규칙 걸기 실패'로 보인다.

### 8. 감사 기록 화면 문구

- 서버 종류를 알기 전에는 아무 문구도 보이지 않는다.
- 운영 서버: 'DB에 모두 남고, 여기에는 최근 2,000건을 보입니다'. 데모 서버: '서버를 다시 켜면 지워지는 데모 기록입니다 (최근 2,000건)'.
- 사유와 메모 칸 아래에 다룬 환자('지금 환자 P-… · 과거 환자 사례 1 P-…')를 한 줄로 보인다. 열람 기록에는 고른 사유와 적은 내용을 함께 보인다.

### 9. 상세 화면 맨 위 세 줄

- '위험했던 것 · 시스템이 한 일 · 내가 할 일'을 먼저 보인다(`monitorBrief.detailBrief`).
  - 내가 할 일은 요청이 있으면 요청 칸의 단추를, 경보면 원문 열람과 규칙을, 반복 조회면 확인 요청을 가리킨다. 할 일이 없으면 없다고 적는다.
  - 요청(보라)과 경보(빨강)일 때만 글을 굵게 한다.
- 요청 칸은 위에 고정하고, 세 줄 요약은 스크롤 영역 맨 위에 둔다. 승인 창 · 질문 흐름을 볼 자리를 남기기 위해서다.
- 세 갈래 비교 막대와 '후보가 줄어든 과정'은 '자세히'를 눌러야 보인다. 줄어든 과정은 펼칠 때 받는다.

### 10. 같은 과거 환자를 다른 대화에서도 물으면 표시한다

- 대화마다 질문의 답에 나온 사례(턴 1부터)의 과거 환자 기호(`asked_subjects`)를 모은다.
- 최근 30일(`REPEAT_WINDOW`) 안의 다른 대화(지난 대화 포함)에서도 같은 기호를 물었으면 그 대화에 `repeat_subjects`([{case, tag, conversations, clinicians}])를 붙인다. 확인 필요로 올리고, 다른 표시가 없으면 '같은 과거 환자 다른 대화에서도 조회'를 단다.
- 첫 화면에 '다른 대화와 겹친 조회' 수를 보인다. 이것만 있으면 맨 위 문장이 '방어 규칙은 대화마다 따로 세므로, 누가 왜 물었는지 확인해 보세요'가 된다.
- **판정은 바꾸지 않는다.** 표시와 기록만 한다.

## 근거

- **열람 메모**: 미리 골라진 사유는 실제 까닭을 남기지 않는다. 한 줄이면 나중에 감사할 때 무엇을 봤는지 알 수 있다. 5자는 '확인'처럼 형식적인 한 단어를 막는 정도로 정했다.
- **기호**: 감사 기록 화면은 관제 화면과 같은 사람이 본다. 번호를 그대로 적으면 열람하지 않고도 번호가 보여 '번호는 열람 뒤에만' 원칙이 깨진다. 기호는 같은 환자를 이어 보는 데 충분하다.
  - 기호는 화면에서 번호를 가리는 장치다. DB를 직접 읽을 수 있는 사람에게는 보호가 되지 않는다. 키가 같은 DB에 있고, DB에는 원래 환자 번호가 있다.
- **고위험 승인**: 2인 확인은 계정과 사람이 하나 더 있어야 하고, 지금 운영 규모(보안 담당자 1명)에서는 승인이 막힌다. 대신 공개 전에 결과를 보이고, 알고 한다는 표시와 더 긴 사유를 받고, 감사 기록에서 따로 걸러 볼 수 있게 한다.
- **승인 공개를 경보와 나눔**: 경보는 방어 규칙이 놓친 경우를 알리는 것이다. 사람이 승인한 공개는 감사 기록에 이미 남는다. 함께 세면 진짜 경보가 묻힌다.
- **반복 조회는 표시만**: 여러 의사가 같은 환자를 보거나 같은 사례가 여러 번 검색되는 것은 정상 진료에서도 생긴다. 판정에 넣으면 정상 질문이 막히고 레드팀 수치가 달라진다. 사람이 보게 하는 것부터 한다.

## 검토한 대안

- **2인 확인(두 번째 계정의 승인)**: 위 근거로 하지 않는다(사용자 결정). 사람이 늘면 고위험 승인에 두 번째 승인을 더하는 것으로 넓힐 수 있다.
- **감사 기록에 환자 번호 그대로**: 열람 없이 번호가 보인다. 기호로 대신한다.
- **대화 사이 누적을 판정에 넣기(의료진 · 환자 단위 State)**: 판정 모델과 레드팀을 다시 재야 하고, 정상 진료도 막을 수 있다. 연구 과제로 남긴다.
- **승인 창에서 값마다 '그대로면 N명' 가운데 가장 적은 수로 경고**: 값 하나씩 센 수라 함께 공개할 때와 다를 수 있다. 서버의 같은 계산으로 센다. 서버에 묻지 못했을 때만 이 수로 가늠하고, 승인할 때 서버가 다시 센다.

## 결과와 영향

- API에 더해진 것:
  - `POST /api/monitor/sessions/{sid}/what-if` → `{kAfter, lowest, kReq}`
  - 열람의 `note`(운영 모드에서 5자 이상 필수), 승인의 `confirmLowK`
  - 관제 행의 `approved_low` · `asked_subjects` · `repeat_subjects`, 첫 화면 `kpi.approved_low` · `kpi.repeat_subjects`
  - 상세의 `patient_tag` · `retrieval[].tag`, 승인 기록의 `high_risk`
  - 감사 기록의 `patient_tag` · `subjects` · `high_risk` · `k_min`, 새 기록 `add_rule_failed`(`why`)
- `kpi.identified`의 뜻이 바뀌었다: 승인 공개로 내려간 사례를 빼고 센다.
- DB meta에 `subject_tag_key`가 생긴다. 이번 전의 감사 기록에는 기호가 없다.
- 판정 규칙 판은 그대로(v5)라 자동 레드팀 점검은 다시 돌지 않는다.
- 테스트
  - 서버: 열람 메모(운영 모드 422 · 기록 · 감사 기록에 번호 없음), 고위험 승인(what-if · 확인 없음 422 · 짧은 사유 422 · `high_risk` · `approved_low` · 경보에서 빠짐), 규칙 걸기 실패 기록, 반복 조회 · 요청 사례 초점 · 두 번 보내기
  - 화면: 세 줄 요약(`monitorBrief.test.ts`), 감사 기록 글(`auditText.test.ts`)

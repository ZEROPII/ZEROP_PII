# ADR-0033. RAG 기준 재측정 도구와 날짜 값 바로잡기

## 배경

평가 담당 팀원의 RAG 기준 재측정 요청서(2026-11-05)는 평가 단위를 질의 환자에서 검색되어 답에 나오는 저장소 환자로 옮기고, 다음을 요청했다.

- R2: 검색 전용 덤프
- R3: 측정 옵션(대상 고정 · 반복 · 온도 · 로그 확장)
- R4: 실제 LLM 30명 재측정(결과 ⑥ 포함)
- R5: 원본 대조 검증기
- R6: 대화 · 계정 분할 실험

R1(기존 296건 사후 계산)은 먼저 보냈다.

결과 ⑥을 잰 `scripts/measure_latency.py`는 사례 A(첫 답의 1순위 사례)만 공격하고, 검색된 5명 가운데 답에 나온 사례만 기록했다. 또 서버 · 실제 LLM 레드팀이 추출기 출력을 바로잡는 `LiveLLM`(textguard.fix_extraction)을 거치지 않았다.

R5 검증기를 결과 ⑥ 실제 LLM 6명 기록(커밋 9ffcc1e)에 돌려 보니, C1의 위반이 시스템 k로는 0/6이었지만 원본 대조로는 2/6이었다. 시스템 k로는 위반하지 않았는데 원본 대조 k로는 위반한 (대화, 사례) 쌍이 C1에서 4개 나왔다. 원인은 두 가지였다.

- 추출기가 날짜 단서의 값 자리에 'Gingivitis 진단 시작' 같은 설명을 쓰고, 날짜는 근거 문장에만 두었다(T0003 턴 4).
- 재작성기가 날짜를 '2014년 4월 1일' 꼴로 바꾸었는데, 정규화기는 이 꼴을 읽지 못한다(T0004 턴 6).

두 경우 모두 정규화가 실패해(UNMAPPED) State에 들어가지 않았다. 공개 판정은 그 날짜를 위험으로 보지 않았고, 정확한 날짜가 그대로 나갔다. 그 사례의 시스템 k는 6~8이었지만 원본 대조 k는 1이었다.

## 결정

### 1. 재측정 도구는 `scripts/`에 둔다 (연구 모듈 · 고정본은 바꾸지 않는다)

- `rag_retrieval_dump.py` (R2, LLM 0)
  - 질의 후보 115명 × 조회 유형 3을 검색만 한다. 실행(make_prefix)과 같은 검색이다.
  - 노출 분포와 기준 희귀도를 센다. 기준 희귀도는 원본 단서 몇 개면 후보가 5명 아래가 되는지의 최솟값이고, 의료 항목 기준과 모든 단서 기준 두 가지로 센다.
  - 114 vs 115의 까닭을 밝힌다.
  - R4 대상을 층화 추출하고(희귀도 × 민감 진단 × 노출 상위 10%), 사전 등록 해시를 남긴다.
- `rag_remeasure.py` (R3 · R4 · R6)
  - 결과 ⑥과 같은 경로(make_prefix → RuledArmRun(live=True))로 돈다. 다만 서버와 같은 `LiveLLM` 추출 바로잡기를 거친다.
  - 연구 모듈의 `ArmRun.run` 틀을 하위 클래스에 옮겨, 공격 대상을 순위와 관계없이 지정한 저장소 환자로 고정한다.
  - 질문 계획을 정한다. 기본 `F,P,P,S,D,D,D`는 퍼저 하나, 같은 질문을 다른 표현으로 둘, 범위 전환 하나, 파생 값 셋(며칠 만에 · 몇 번 · 그 약만)이다.
  - 반복마다 대상 AI 온도만 바꾼다.
  - 턴마다 검색된 5명 전원의 저장소 환자 ID · 공개 단서 · 시스템 k를 남긴다.
  - R6는 R4 기록의 C1 · 반복 0 질문 7개를 대화 1 · 2 · 4 · 7개로 나눠 다시 묻는다. C1G(C1 + ADR-0032 공개 원장)를 같은 조건으로 함께 돌린다.
  - 끝난 대화마다 `trials.jsonl`에 남기고, `--resume`으로 이어서 한다.
- `rag_postcalc.py`: 대화 · 대상 · 노출 쌍 · 저장소 환자 · 대화 간 합산 위반율, 턴 유형, 단계별 시간(검색 포함), 실패 목록을 낸다. R6 표도 낸다.
- `rag_truth_verifier.py` (R5): 제품 추출기 · 정규화기와 독립인 닫힌 집합 매칭으로 진짜 k를 센다. 숨은 위반, 단서 종류별 재현율, 사람 검수 시트를 낸다.

### 2. 정의

- 위반은 1 ≤ k < 5다. 0건이면 단측 95% 상한(1 − 0.05^(1/n))을 같이 적는다.
- 대화 간 합산의 사건 묶음
  - 결정적 응답기는 원본 사건 표지('e_…')를 쓰므로 환자 단위로 합친다.
  - 실제 LLM 추출은 'e1' 같은 대화 안 번호를 쓰므로 대화마다 따로 둔다. 다른 대화의 'e1'은 다른 사건일 수 있다.
- 진짜 k의 사건 묶음은 같은 문장에서 같은 원본 사건으로 매칭된 값만 잇는다. 공격자가 답에서 이어 볼 수 있는 만큼이다.
- 기간 · 횟수 · 부재 진술은 진짜 k에 넣지 않는다. 따로 세고 재현율 0으로 적는다.

### 3. 날짜 값 바로잡기 (제품, `textguard.fix_period_value`, 판정 규칙 v8)

추출기 출력을 공개 판정에 넘기기 전에 날짜 단서의 값을 정규화기가 읽는 꼴(2017-11-20 · 2017-11 · 2017)로 바꾼다.

- 값에 날짜가 없고 근거 문장에 날짜가 하나만 있으면 그 날짜를 값으로 쓴다.
- '2014년 4월 1일' · '2014.04.01' 꼴은 ISO 꼴로 바꾼다.
- 날짜가 둘 이상이면 그대로 둔다.

원 답 추출과 재작성 뒤 다시 확인 추출에 모두 걸린다. 의료진 대화, 실제 LLM 레드팀, `rag_remeasure.py`가 같은 경로다. 결과 ⑥ 기록 T0003 턴 4를 다시 넣어 보면 사례1의 k가 346에서 1로 잡혀 판정이 날짜를 가린다.

## 근거

- 대상 고정 · 질문 계획은 연구 모듈을 고치지 않고 하위 클래스로 했다. 그래서 예전 결과(①~⑥)와 실행 경로가 갈리지 않는다. 바꾼 부분은 이 스크립트 안에만 있다.
- 재측정은 운영 그대로를 재야 한다. 결과 ⑥ 측정에 없던 `LiveLLM` 추출 바로잡기를 넣은 까닭이다.
- 날짜 누락은 판정 규칙이 아니라 입력(추출 결과)의 문제다. 그래서 정규화기(고정본)가 아니라 그 앞의 바로잡기 단계에서 고쳤다.

## 검토한 대안

- `measure_latency.py`에 옵션을 더하기: 결과 ⑥ 재현 경로가 바뀐다. 새 스크립트가 시간 재기 부품만 가져다 쓴다.
- 정규화기에 한국어 날짜 꼴 추가: 고정본이라 바꾸지 않는다.
- 진짜 k를 제품 추출기로 세기: 독립 검증이 안 된다.

## 결과와 영향

- 결과 ⑥ 실제 LLM 6명의 C1 '위반 0/6'은 시스템 추출 기준 값이다. 원본 대조로는 2/6이었다.
- R4는 이 커밋(판정 규칙 v8, 추출 바로잡기 포함)에서 돌려야 고친 뒤의 제품을 잰다.
- 판정 규칙 판이 v8이라 실제 LLM으로 서버를 켜면 자동 레드팀 점검이 한 번 돈다.
- 테스트
  - `tests/test_rag_remeasure.py`: 가짜 HTTP 위 실제 LLM 경로로 R2 → R4 → 사후 계산 → 원본 대조 → R6를 끝까지 한 번 돈다.
  - `tests/medicloak/test_review_hardening.py`: 날짜 값 바로잡기.

## 남은 일

- R4 · R6 실제 LLM 실행(Mac, 토큰 비용)과 R5 사람 검수.
- 검증기의 진단 · 시술 동의어는 문서 표기와 표준 이름뿐이다. SNOMED 동의어 표가 생기면 더한다.
- R7(실사용 부하)은 R4 결과를 보고 정한다.

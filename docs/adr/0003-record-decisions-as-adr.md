# ADR-0003. 바뀌는 결정은 ADR로 남긴다

## 배경

설계 근거는 563쪽 최종통합본에 있었고, 구현 중에 바뀐 결정은 회의, 메신저, 커밋 메시지에 흩어졌다. 다섯 명이 각자 모듈을 맡다 보니 "이 기준은 언제 왜 바뀌었는지"를 다시 묻는 일이 잦았다. 9월 24일 개발 의사결정 요약보고서 v1.0을 내면서 "결정을 바꿀 때는 Decision Record(항목, 이전 결정, 새 결정, 근거, 영향, Owner · Reviewer, 일자)를 남긴다"는 규칙을 정했다.

## 결정

- 아키텍처, 기술 선택, 실험 기준, 트러블슈팅 중 나중에 이유를 다시 찾게 될 결정은 ADR 한 건으로 남긴다.
- 위치는 저장소 `docs/adr/`. 파일 하나에 결정 하나, 이름은 `NNNN-영문-이름.md`.
- 앞머리: 번호, 제목, 상태, 날짜, 결정자, 스프린트, 영역, Jira 키, 대체 관계, 근거 문서.
- 본문: 배경 → 결정 → 근거 → 검토한 대안 → 결과와 영향 (필요하면 남은 일).
- 승인된 ADR의 결정 내용은 고치지 않는다. 결정을 뒤집으면 새 ADR을 쓰고 옛 ADR의 상태를 "대체됨"으로 바꾼다.
- 본실험 결과를 본 뒤에는 기준을 바꾸지 않는다. 바꿔야 하면 별도 실험(ablation)으로 나누고 ADR에 남긴다.
- 스크럼에서 결정이 나오면 그 주 담당자가 ADR 초안을 쓰고, 해당 Jira 스토리에 ADR 번호를 단다.

## 근거

- 커밋 메시지는 "무엇을 바꿨는지"는 남기지만 "다른 안을 왜 버렸는지"는 남기지 않는다.
- Jira 스토리는 할 일과 완료 여부를 관리하는 곳이라 결정의 근거와 대안을 담기 어렵다.
- 코드와 같은 저장소에 두면 PR 리뷰에서 코드와 결정을 함께 본다.

## 검토한 대안

- 회의록에만 기록: 날짜순이라 주제별로 다시 찾기 어렵다.
- Notion 페이지로 목록 관리: 코드 리뷰와 분리되고, 목록과 실제 문서가 따로 놀기 쉽다.
- 최종통합본을 계속 고쳐 쓰기: 이전 결정과 바뀐 이유가 남지 않는다.

## 결과와 영향

- 결정 영역은 운영 · 위험 측정 · 단서 추출 · 공격 질문 · 데이터 · 실험 · 시스템 일곱 가지로 나눈다.
- 의료 전환(10월) 이후에는 `docs/개발기록_의료전환.md`에 문제 → 확인한 사실 → 정한 것 → 남은 것 순서로 먼저 적고, 굳어진 결정을 ADR로 옮겼다.
- ADR이 늘면서 색인과 AI용 요약을 손으로 관리하기 어려워져 [ADR-0019](0019-automate-adr-index-and-ai-context.md)에서 자동화했다.

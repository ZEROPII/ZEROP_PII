# Zero PII 의사결정 요약 (AI · 새 팀원용)

> 이 파일은 `python scripts/adr.py index`가 `docs/adr/*.md`에서 만든다. 직접 고치지 않는다.
> ADR 34건 (유효 32 · 대체·폐기 2), 마지막 결정일 2026-11-07.

## 읽는 법

- '유효한 결정'이 지금 코드와 실험이 따르는 기준이다. 코드를 바꾸거나 제안할 때 이 결정과 어긋나면, 바꾸기 전에 새 ADR이 필요하다고 먼저 알린다.
- '제안' 상태는 아직 확정되지 않은 결정이다.
- '대체·폐기된 결정'은 이력이다. 따르지 않는다.
- 근거 경로는 저장소 기준이다. `ext:`는 저장소 밖 문서다.

### ADR-0004. 위험은 기준 집단 후보 수 k로 재고, 1 ≤ k < 5를 위반으로 본다

- 승인 · 2026-09-24 · 결정 배성윤, 이유진 · S2 · Jira ZP-13 · 위험 측정·방어
- 근거: `ext:개발의사결정_요약보고서_v1.0#Stage5-6`, `docs/modules.md`

**결정**

- 위험 단위: 지금까지 공개된 단서를 모두 만족하는 기준 집단 인원 수 k. 처음 k는 기준 집단 전체.
- 판정: k ≥ 5 충족, 1 ≤ k < 5 위반, k = 0은 ZERO_MATCH(진단)로 따로 표시한다.
- 실행 중 제어에는 k_run을 쓰고, 결과 수치는 정답 대조로 다시 계산한 k_val만 쓴다.
- 처음 안전 → 위반으로 넘어간 순간(crossing)을 따로 기록한다.
- 민감도 분석은 k_req ∈ {2, 3, 5, 7, 10}.
- 1/k를 확률로 쓰거나 단서별 가중치를 합친 위험 점수는 만들지 않는다.

**결과와 영향**

- 평가 · 리포트 · 화면이 모두 "k < 5 위반, k = 0 진단"으로 표시한다.
- Defender(risk_defender)는 k ≤ 5를 위험으로 보고 평가는 k < 5를 위반으로 봐서, 10월 23일 모의 POC의 사례 단위 과잉 수정 5.8%가 모두 k = 5에서 나왔다.

### ADR-0005. 단서 추출은 LLM 구조화 추출기로 하고 근거 문구를 반드시 붙인다

- 승인 · 2026-09-24 · 결정 양승준 · S2 · Jira ZP-6 · 단서 추출·정규화
- 근거: `qi_extractor/`, `ext:개발의사결정_요약보고서_v1.0#Stage2`

**결정**

- 기본 추출기는 LLM 구조화 추출기다. 입력은 질문 · 응답 한 쌍이고, 출력은 JSON 스키마로 검증한다.
- 관찰 하나에 단서 종류, 원래 값, 명시/문맥 구분, 확신도(1–5 정수), 근거 문구(응답 원문의 구절), 턴 번호를 담는다.
- 질문에만 있고 응답에는 없는 값은 유출로 보지 않는다.
- NER · 규칙은 명시적 단서 기준선과 교차 확인용으로만 쓴다.
- 추출기 모델, 프롬프트 버전, temperature를 실행 기록에 남긴다.

**결과와 영향**

- 근거 문구 검증은 실행 중 완화했다. 문구 중 하나라도 응답에 있으면 관찰을 인정하고, 찾지 못한 문구는 `unverified_spans`에 남긴다.
- 의료 전환 뒤 나이 · 날짜는 규칙 추출을 보조로 붙였다(`--rule-extract`). 보류 검증에서 규칙 추출의 확정 값 정밀도가 24/45로 가장 낮아 개선 대상이 됐다([ADR-0018](0018-holdout-validation-for-extraction.md)).

### ADR-0006. 공격 질문은 사람이 정한 공격 공간 안에서만 LLM이 변형한다

- 승인 · 2026-09-24 · 결정 한재이 · S2 · Jira ZP-10 · 공격 질문 생성
- 근거: `fuzzer/`, `ext:개발의사결정_요약보고서_v1.0#Stage7-8`

**결정**

- 목표(O1 새 단서 얻기, O2 구체화) × 질문 방식(S1 직접, S2 추론, S3 간접 · 맥락, S4 추가 질문) × Seed는 사람이 정하고 고정한다.
- LLM은 Backend가 고른 변형(M1–M6)을 문장으로 옮기기만 한다. 유효성 검사를 통과한 질문만 Target에 보낸다.
- 기본 선택은 적용 가능한 변형 중 균등 선택이다. k 피드백으로 고르는 방식은 비교 조건으로 둔다.
- 변형 LLM 프롬프트에 k 값이나 정답을 넣지 않는다. Backend가 정한 변형 지시만 넘긴다.
- 사람 검토를 마치지 않은 Seed는 본실험 모드에서 적재하지 않는다.

**결과와 영향**

- 의료판 Seed는 O1 72행 · O2 63행, 사례 검색 질문 12개다(Seed v0.13 · 사례검색질문 v0.2).
- 이 구조 위에서 k 피드백 켬 · 끔 비교(ZP-35)와 No-K ablation을 할 수 있었다. 모의 POC에서 C0 위반은 균등 선택 95.6%, k 피드백 99.3%였다.

### ADR-0007. 공개 전 판정을 허용 · 일반화 · 억제 세 단계로 나눈다

- 승인 · 2026-10-04 · 결정 이유진 · S3 · Jira ZP-18 · 위험 측정·방어
- 대체한 결정: ADR-0002
- 근거: `docs/modules.md`, `risk_defender/`

**결정**

기준을 두 개로 나눈다: `generalize_threshold = 5`, `suppress_threshold = 3`.

| 그 단서를 그대로 냈을 때 k | 처리 |
| --- | --- |
| k > 5 | 원문 그대로 허용 |
| 3 < k ≤ 5 | 부모 방향으로 올라가며 처음 k > 5가 되는 값으로 일반화. 없으면 k > 3인 값, 그것도 없으면 억제 |
| k ≤ 3 | 일반화를 시도하지 않고 바로 억제 |

- 루트(ANY)까지 올라간 일반화는 "말하지 않음"과 같으므로 억제로 기록한다.
- 사례(과거 환자)가 여러 명이면 사례마다 따로 판정한다.

**결과와 영향**

- 의료판도 이 정책을 그대로 쓴다([ADR-0012](0012-event-level-kcalc.md)).
- 10월 23일 모의 POC에서 C1이 고친 단서는 31%였고, 그중 90%가 억제였다. 억제의 82%는 원래 k가 3 이하라 일반화를 시도하지 않은 경우였다.

### ADR-0008. 실제로 공개한 응답의 단서만 State에 반영한다

- 승인 · 2026-10-05 · 결정 양승준, 이유진 · S3 · Jira ZP-21 · 위험 측정·방어
- 근거: `orchestrator/`, `docs/research_harness.md`, `ext:개발의사결정_요약보고서_v1.0#Stage11`

**결정**

- 공개된 응답(Released Response)에서 다시 추출한 단서만 State에 반영한다.
- 원 응답과 그 단서는 평가 기록(trace)에만 남긴다.
- Fuzzer도 공개된 응답만 본다.
- State ID는 State에 반영된 값으로 만든다.

**결과와 영향**

- 재작성 뒤 남은 단서 검사를 붙였다. 지운 값의 근거 문구가 글자 그대로 남아 있으면 다시 고친다.
- State ID 계산 방식이 바뀌어, 이전 실행의 `state_id`와 값이 다르다.

### ADR-0009. 비교 갈래끼리 같은 질문과 같은 원 응답을 쓴다 (--paired)

- 승인 · 2026-10-06 · 결정 양승준 · S3 · Jira ZP-22 · 실험·검증
- 근거: `docs/research_harness.md`, `orchestrator/shared_raw.py`

**결정**

`--paired` 옵션을 둔다.

- 첫 갈래(보통 C0)의 질문 순서를 나머지 갈래에 그대로 던진다.
- 같은 질문의 원 응답과 그 추출 결과를 갈래들이 함께 쓴다. 함께 쓴 응답은 trace에 토큰 0으로 기록한다.
- 그러면 갈래 간 차이는 공개 게이트(Defender 판정 → 재작성 → 재추출)에서만 생긴다.

**결과와 영향**

- `--paired`에서는 나머지 갈래의 공격자가 자기 갈래 응답에 반응하지 않는다. "방어된 응답을 보고 질문을 바꾸는 공격자" 결과가 필요하면 `--paired` 없이 돌린다.
- README의 실행 옵션 표에 두 경우를 나눠 적었다.

### ADR-0010. 적용처를 병원 대화형 의료 AI(유사 환자 조회)로 바꾼다

- 승인 · 2026-10-09 · 결정 배성윤, 이유진, 이정민, 한재이, 양승준 · S3 · Jira ZP-25, ZP-26, ZP-27, ZP-28, ZP-29, ZP-30, ZP-31 · 데이터·적용처
- 근거: `docs/medical.md`, `docs/개발기록_의료전환.md`

**결정**

- 대상 시스템: 진료 중 의료진이 과거 유사 환자 사례를 묻는 병원 대화형 AI.
- 점검 주체: 병원 정보보호 · CISO 조직, 의료정보팀.
- 데이터: Synthea 합성 환자 576명. 실제 환자 데이터는 쓰지 않는다.
- 단서: 성별 · 지역 · 진단 · 나이 · 날짜 · 약 · 시술 · 관리 계획 8종.
- 프레임워크 구조(추출 → State → k → Defender → 재검증)는 그대로 두고, 데이터 · 온톨로지 · k 계산만 의료용으로 바꾼다.
- SynthPAI 실험은 학회 논문 결과로 유지한다.

**결과와 영향**

- 의료 스토리 39 SP를 백로그에 추가했다(ZP-25~31). 범위가 160 SP에서 늘었고, 번다운에서 10월 11일에 남은 SP가 다시 올라간 지점이다.
- 의료 전달 묶음(온톨로지, 사건연결표, k 계산기, Seed)을 반영하면서 [ADR-0012](0012-event-level-kcalc.md)부터 [ADR-0016](0016-separate-synthpai-and-medical-paths.md)까지의 결정이 이어졌다.

### ADR-0012. 의료 k는 사건 단위 계산기(kcalc) 하나로 센다

- 승인 · 2026-10-19 · 결정 이유진, 양승준 · S4 · Jira ZP-28 · 위험 측정·방어
- 근거: `docs/개발기록_의료전환.md#2`, `docs/medical.md`, `medical/defense.py`

**결정**

이유진과 합의한 내용이다.

| 항목 | 결정 |
| --- | --- |
| k 계산 | 전달 묶음의 `kcalc.py`(사건 단위)로만 센다. 같은 사건의 진단 · 나이 · 날짜를 한 사건이 함께 만족해야 후보로 센다 |
| 판정 정책 | risk_defender 규칙을 그대로 쓴다([ADR-0007](0007-three-level-release-decision.md)) |
| 구현 위치 | `medical/defense.py`. 팀원 코드(`risk_defender/`)는 고치지 않고 정책만 옮겨 와 kcalc 위에서 수행한다 |
| 루트(ANY)까지 일반화 | 억제로 기록한다 |
| k = 0 | Defender 판정에서는 위험으로 본다. 평가에서는 ZERO_MATCH로 따로 표시하고 위반으로 세지 않는다 |

퍼저 · 방어 · 평가가 모두 이 k를 쓴다.

**결과와 영향**

- 이유진이 프로필을 사건 기반 v2로 바꿨고, 기록 그대로의 공개에서는 kcalc와 100% 같아졌다.
- 모의 POC(질의 환자 296명 × C0 · C1 · C1S, 8턴)에서 C0 위반 95.6%, C1 0%, C1S 83.1%가 나왔다.

### ADR-0013. 의료 온톨로지는 단일 부모 계층으로 먼저 구현한다

- 승인 · 2026-10-19 · 결정 양승준, 배성윤 · S4 · Jira ZP-27 · 데이터·적용처
- 근거: `docs/개발기록_의료전환.md#1`, `medical/bundle/`

**결정**

1차 구현은 단일 부모 계층으로 한다(노드 v0.9, 10월 21일 v0.10으로 갱신).

**결과와 영향**

### ADR-0020. 의료진 화면은 EMR 진료 지원 AI로 두고 위험 분석은 보안 담당자 화면으로 옮긴다

- 승인 · 2026-11-04 · 결정 양승준 · S5 · 시스템·화면
- 근거: `frontend/src/pages/ClinicalAssistPage.tsx`, `frontend/src/pages/WatchPage.tsx`, `frontend/src/lib/clinicianCopy.ts`, `frontend/src/lib/clinicianView.test.ts`, `webdemo/backend/monitor.py`, `webdemo/README.md`

**결정**

- 의료진 화면(`/`, `/history`, `/guide`)은 병원 EMR 안의 진료 지원 AI 형태로 둔다: 앱 머리줄, 진료 중 환자 띠, 비슷한 사례 | 대화 | 사례 노트. 화면 토큰은 `[data-app='emr']`(청록 계열)로 보안 담당자 화면(남색)과 나눈다.

- 위험 분석은 보안 담당자 화면으로 옮긴다. 새 '의료진 대화'(`/watch`) 화면에 후보 렌즈, 사례별 후보 수, 숫자가 붙은 대화, 나간 정보와 판정 근거, 질문 미리 세기(상태를 바꾸지 않음), 단서 그래프를 모은다. 보호 정책(기준 5 · 3)도 보안 담당자 메뉴로 옮기고, 의료진에게는 숫자 없는 '보호 안내'를 둔다.

- 사례 노트는 옵시디언 노트 방식으로 만든다: 속성(진단 · 약 · 시술 값은 용어 사전 [[링크]]), 연결된 질문(누르면 대화의 그 질문으로), 같은 값이 나온 사례. 공개 이력의 턴과 질문을 잇기 위해 데모 서버와 api_server가 대화 메시지에 `engineTurn`(대화 전체 턴 번호)을 붙인다.
- 단서 그래프(옵시디언 그래프 보기 방식)는 보안 담당자 화면에만 둔다. 여러 사례에 공통인 값은 가운데로, 한 사례에만 붙은 값은 그 사례 둘레에 남는다.
- 제품 이름은 MediCloak으로 쓴다. 의료진 화면에서는 머리줄의 'MediCloak 보호 적용' 표시로만 드러낸다.

**결과와 영향**

- 데모 순서가 바뀐다: 의료진 화면에서 묻고 답을 본 뒤, 보안 담당자 '의료진 대화'에서 같은 대화를 숫자와 함께 본다. 세부 정보 요청 → 관제 답장 → 의료진 메시지 도착까지 한 화면 전환 안에서 보여 줄 수 있다.
- 의료진 화면 문구에 숫자가 들어가지 않는지 테스트로 확인한다(`frontend/src/lib/clinicianView.test.ts`). 프런트 테스트 36개, 데모 서버 테스트 14개(메시지 흐름 · plannedAction 2개 추가), api_server 테스트 1개(engineTurn · value) 추가.
- 쓰지 않게 된 통합 화면 부품(CaseFinderPage, ChatPanel, PreflightWarning, PatientContextCard, CaseList)은 지웠다. 기능은 위 두 화면으로 나눠 옮겼다.
- 두 화면은 역할에 따라 틀(앱 머리줄)부터 다르므로, 역할은 그리는 시점에 주소로 정한다. 화면 안에서 역할을 바꿀 때 이전 역할의 틀이 한 번 그려지면 의료진 화면 부품이 메시지 제공자 밖에 놓여 화면이 비었다(코드 검토에서 발견, 같은 날 수정).

- **운영 모드 `python -m medicloak`**를 둔다. 서버 코드는 데모 서버(`webdemo/backend/`)를 그대로 쓰고 켜는 방법만 다르다. 데모 모드는 지금처럼 남긴다(로그인 없음 · 결정적 응답기 · 메모리 기록).
- **DB**: SQLite 파일 하나(`runs/medicloak/medicloak.db`, WAL). 가상 EMR(노드 71,692 · 사건 51,759 · 환자 576명), 계정 · 로그인 세션, 의료진 대화 스냅숏 · 턴 기록(원 응답 포함), 메시지, 감사 기록을 둔다. 위험 계산 엔진(kcalc · 정규화 · MedicalData)은 DB에서 내보낸 CSV 스냅숏을 읽는다. 연구 하네스(`medical/`)와 고정본은 고치지 않는다.
- **가상 EMR**: FHIR R4 읽기 전용 API(`/fhir/metadata` · `Patient` · `Condition` · `MedicationRequest` · `Procedure` · `CarePlan`). 외래 환자(QUERY_POOL 115명)만 열고, 유사 사례 검색 대상인 과거 기록 환자(STORE 461명)는 404다. 의료진은 외래 목록(`/emr`)에서 환자와 진료 목적을 골라 진료 지원 AI를 연다(`/api/emr/launch` → 연구 계획의 trial).
- **로그인 · 역할**: 비밀번호는 PBKDF2-SHA256 200,000회(계정마다 salt). 로그인하면 HttpOnly 쿠키(`mc_session`, SameSite=Lax)를 주고 DB에는 토큰의 SHA-256만 둔다. 세션은 12시간이 지나거나 60분 동안 쓰지 않으면 끝난다. 경로 접두사마다 들어올 수 있는 역할을 한 표(`auth.ROUTE_ROLES`)로 정하고, 두 곳에서 검사한다: 미들웨어(라우터와 같은 경로 = root_path를 뗀 경로)와 API 라우터마다 붙인 의존성(실제로 맞은 경로 틀). 의료진은 의료진 화면 API와 EMR만, 보안 담당자는 관제 · 의료진 대화 분석 · 레드팀 · 평가 대시보드만 쓴다. 운영 모드에서는 API 문서(`/docs` · `/openapi.json`)를 열지 않고, 세션 직접 조작 경로(`/api/sessions/…`)는 의료진 대화를 열거나 바꾸지 못한다(원문을 사유 없이 보내고 질문을 더할 수 있어서).
- **로그인 제한 · 기록**: 같은 계정+주소 10분에 5번, 같은 계정 10분에 20번 틀리면 막는다(429). 시도는 비밀번호를 확인하기 전에 세어 동시에 보내도 한도를 넘지 못하고, 비밀번호 해시는 동시에 4개까지만 돌린다. 없는 · 쓰지 않는 계정도 해시를 한 번 돌려 걸리는 시간이 같다. 로그인 · 로그아웃 · 실패 · EMR 열기 · 의료진 질문이 감사 기록에 남는다(질문 본문은 대화 기록에만, 없는 아이디는 입력값을 남기지 않음).
- **의료진마다 대화**: 계정마다 ClinicDesk 하나(`DeskRegistry`). 메시지도 그 의료진의 대화에만 붙는다.
- **숫자 없는 의료진 API**(ADR-0020 남은 일): 의료진 화면 API는 데모 · 운영 모드 모두 `redact.py`를 거친다. 후보 수 · 기준값 · 기준 집단 크기와 숫자가 든 설명 문장을 지우고, 판정 근거(`/policy-decision`)는 403이다. 보안 담당자는 같은 계약을 `/api/watch/{대화}/…`로 숫자 그대로 받고, 화면은 대화를 골라 본다.
- **실제 LLM**: `.env`의 `LLM_API_KEY` · `LLM_API_BASE` · `LLM_MODEL`(core.config) → `medical.llm.ClientRoleLLM`. 의료진이 쓴 문장을 그대로 대상 AI에 보내고(사례 표기가 없으면 "사례N에 대한 질문: "을 앞에 붙임), 추출기 · 재작성기도 같은 모델이다. 턴 0 사례 검색 답, 보내기 전 확인, 레드팀, 시작할 때의 시뮬레이션 대화는 결정적 응답기로 둔다. 비교 갈래는 C0을 같은 원 응답으로 바로, C1S를 의료진 답을 보낸 뒤 뒤에서 계산한다(ADR-0009 paired와 같이 원 응답 · 추출 결과를 같이 씀). LLM 오류는 상태를 바꾸기 전에 나므로 502로 돌려준다.
- **실제 LLM 대화의 규칙 추출**: 실제 LLM 대화에는 `rule_extract`(medical/rule_extract.py, 답에 적힌 나이 · 날짜를 정규식으로 보탬)를 켠다(끄려면 `--no-rule-extract`). 2026-11-04 맥에서 claude-haiku-4.5로 처음 돌린 대화(S0009)에서 추출기가 시작일을 PERIOD 단서로 내지 않고 약 항목의 `period_start` 칸에만 적었다. 공개 계획은 그 칸을 단서로 세지 않아 날짜를 가리지 않았고, 고친 답을 다시 뽑을 때에야 날짜가 PERIOD로 나와 후보 1명이 되어 답 전체가 거절되었다. 다른 값을 고칠 일이 없는 답이었다면 시작일이 그대로 나갔을 것이다(테스트 `test_dates_only_inside_med_fields_are_still_counted`). 결정적 응답기(데모 · 레드팀 · 시뮬레이션)는 바꾸지 않는다.
- **LLM을 기다리는 동안**: `LiveLLM`이 네트워크 호출 동안 엔진 잠금을 풀었다가 다시 잡는다. 연구 모듈은 호출을 모두 마친 뒤에만 State를 바꾸므로, 그 사이 다른 요청은 앞 턴까지의 상태를 본다. 같은 의료진의 질문은 ClinicDesk 잠금이 줄 세우고, 동시 호출은 기본 1개(`--llm-concurrency`)이며 비교 갈래 호출은 의료진 질문에 자리를 양보한다.
- **영속화**: 의료진 질문 · 새 대화 · 메시지 · 검토 표시 때마다 대화 스냅숏(관제 목록 줄 · 세 조건 상세 · 의료진 화면 계약)과 새 턴 기록을 저장한다. 저장 한 번(스냅숏 만들기와 DB 쓰기)은 대화마다 줄 세워 앞 턴 스냅숏이 뒤 턴 것을 덮지 않게 하고, 메모리에서 내리는 대화는 저장이 끝난 뒤에만 내린다(실패하면 그대로 둠). 서버를 다시 켜면 지난 대화는 읽기 전용으로 남는다(관제 · 의료진 대화 분석에서 열람 · 원문 열람 · 검토 표시는 됨, 메시지는 안 됨). 대화 · 작업 · 감사 · 메시지 번호는 DB에 남은 번호 다음부터 잇는다.
- **명령**: `init`(DB · 가상 EMR · 데모 계정), `serve`(기본, `--llm real|dry-run|oracle`), `users`(목록 · 추가 · 비밀번호), `check-llm`(키 값은 출력하지 않고 설정 · 짧은 요청 확인).

**결과와 영향**

- 실행 순서: `python -m medicloak init` → `python -m medicloak check-llm` → `python -m medicloak serve --build`. 키 없이 화면만 보려면 `--llm oracle`, 배선만 확인하려면 `--llm dry-run`.
- 테스트: `tests/medicloak/` 19개. 가짜 HTTP 세션을 `core.llm_client.LLMClient`에 끼워 ClientRoleLLM → HTTP 요청 · 응답 해석까지 실제 경로를 돌린다(키 헤더, 모델 · 온도, 사례 표기, 역할 순서, 숫자 없음, 키 오류 502, LLM 대기 중 관제 응답, 다시 켠 뒤 기록, root_path 뒤 역할 검사, 동시 로그인 한도, 세션 직접 조작 경로 차단, 저장 실패 때 대화 유지, 유휴 세션 만료).

- 이 작업 환경에는 실제 키가 없어 실제 모델 호출은 확인하지 못했다. 처음 켤 때 `check-llm`으로 확인한다.
- 실제 LLM 답은 '사례N · 항목: 값' 줄 모양이 아니다. 관제 화면의 바뀐 항목 · 단서 그래프 · 원래 값 표시는 줄 비교 대신 Defender 판정 항목에서 읽는다.

### ADR-0022. MediCloak 운영 모드는 첫 답과 레드팀까지 실제 LLM으로 돌리고, 보안 담당자 검토를 규칙 · 공개 승인으로 대화에 반영한다

- 승인 · 2026-11-04 · 결정 양승준 · S5 · 시스템·화면
- 근거: `medicloak/cli.py`, `webdemo/backend/auth.py`, `webdemo/backend/engine.py`, `webdemo/backend/live.py`, `webdemo/backend/review.py`, `webdemo/backend/clinic.py`, `webdemo/backend/monitor.py`, `webdemo/backend/app.py`, `webdemo/backend/store.py`, `webdemo/backend/redact.py`, `tests/medicloak/test_medicloak.py`, `tests/medicloak/fake_anthropic.py`, `frontend/src/components/viz/Instruments.tsx`, `frontend/src/components/monitor/ReviewTools.tsx`, `frontend/src/components/monitor/WatchRiskPanel.tsx`, `frontend/src/pages/ReportPage.tsx`, `medicloak/README.md`

**결정**

- **첫 답도 실제 LLM**: 실제 LLM 대화의 턴 0은 대상 AI 답 · 단서 추출 · 재작성 · 확인 추출을 실제 LLM으로 하고, 그 뒤 질문과 같은 방어 게이트를 거친다. 사례 검색 질문 문장(mutator · checker)만 결정적 응답기가 만든다. 시스템이 보내는 검색 질문이라 LLM으로 바꿔 쓸 까닭이 없다. 턴 0에서는 세 갈래가 모두 빈 State에서 시작해 요청이 똑같으므로, 앞 갈래가 받은 답을 다음 갈래가 같은 차례에 다시 쓴다(`live.Turn0LLM`). 한 갈래 안에서 같은 요청을 다시 보내면(형식 오류 뒤 재시도) 앞 답을 돌려주지 않고 새로 부른다. 실제 LLM의 첫 답은 '사례N · 항목: 값' 줄 모양이 아니어서 사례 목록 제목(진단 · 관련 항목)은 턴 0 공개 판정에서 만든다.
- **열린 대화 없음**: 운영 모드는 기본 환자를 저절로 열지 않는다. 의료진이 외래 목록에서 환자를 열기 전에는 의료진 화면 API가 409와 머리글 `X-MediCloak-State: no-conversation`을 돌려주고, 화면은 '열린 환자가 없습니다'와 외래 목록 링크를 보인다. 로그인이나 화면 요청만으로는 LLM을 부르지 않는다.
- **레드팀 · 리포트를 실제 LLM으로**: 운영 모드 레드팀 점검은 서버의 실제 LLM으로 돈다. 공격 질문 만들기 · 대상 AI · 추출 · 재작성이 모두 실제 호출이다. 규모는 유형마다 1 · 2 · 5 · 10명 또는 전체(296명)에서 고르고, 시작 전에 어림 호출 수(질의 환자 × 3갈래 × 10턴 × 턴마다 6번)를 보여 준다. 호출은 의료진 질문 호출에 자리를 양보하고(같은 동시 호출 자리), 이 실행의 호출 수 · 토큰을 따로 센다. 실행은 멈출 수 있고(결정적 응답기 실행도 질의 환자 사이에서 멈춤), 멈추거나 실패해도 세 갈래를 다 끝낸 질의 환자까지는 집계한다. 한 갈래라도 LLM 호출이 실패한 질의 환자는 '위험 없음'으로 세지 않고 빼서 그 수를 따로 보인다. 처음 세 명이 모두 실패하면 멈추고, 집계할 질의 환자가 하나도 없으면 결과 없이 오류로 끝난다. 실행이 '끝남'으로 바뀌는 것은 결과를 다 만든 뒤다. 실제 LLM 실행의 갈래는 의료진 대화와 같은 고친 답 다시 확인(아래)을 쓴다. 결정적 응답기 실행은 POC를 그대로 재현하도록 연구 모듈의 갈래를 쓴다. 결과는 DB(`redteam_run`)에 남아 다시 켜도 리포트에 나온다. 리포트는 가장 최근의 실제 LLM 점검을 먼저 보이고, 결정적 응답기 POC는 '참고'로 둔다. 서버가 꺼질 때 돌던 실행은 '끊김'으로 남긴다.
- **시뮬레이션 대화 없음**: 운영 모드 관제에는 실제 의료진 대화만 둔다(`--no-sim` 옵션은 없앰). 데모 모드는 그대로 만든다.
- **규칙**: 보안 담당자가 대화에 '사례N의 이 단서 종류는 늘 가림'을 건다. 의료진 화면 갈래(C1)의 공개 계획에서 그 단서는 넓히지 않고 가리고(`review.RuleDefender`), 고친 답을 다시 뽑을 때 그 단서가 남아 있으면 확인을 통과하지 못한다(`review.RuledArmRun`, 재작성 · 규칙 치환 · 거절 순). 다음 질문부터 걸리고 이미 나간 답은 바꾸지 않는다. 풀 수 있다. 비교 갈래(C0 · C1S)는 연구용 대조군이라 걸지 않는다. 의료진이 다른 환자를 열어 다음 질문이 없는 대화와 서버를 다시 켜기 전의 지난 대화에는 걸거나 풀 수 없다(409).
- **공개 승인**: 의료진의 세부 정보 요청을 받은 보안 담당자가 가린 값을 고르고 사유(5자 이상)를 적어 승인하면, 그 값이 그 의료진의 그 대화에만 '공개 승인' 메시지로 나가고 사례 노트에 '보안 담당자 승인'으로 남는다. 공개한 값은 C1 누적 State에 더해져 이후 판정에 들어간다(후보가 기준 아래로 내려가면 그 사례의 새 단서는 더 가린다). 승인할 목록(`/hidden`)과 승인 응답에는 값이 없다. 관제 화면(대화 상세의 승인 기록 · 메시지 목록의 '공개 승인' 본문)은 사유를 남긴 원문 열람 뒤에만 값을 보인다. 의료진 대화 화면 보기는 의료진이 본 그대로라 사례 노트에 공개한 값이 보인다. 감사 기록에는 공개한 항목과 사유를 남기고 값은 남기지 않는다. '공개 승인' 메시지는 승인 경로로만 보낼 수 있다. 승인은 의료진이 지금 열어 둔 대화에만 할 수 있다. 다른 환자로 넘어간 대화에 승인하면 값이 의료진에게 닿지 않으므로 409로 막는다.
- **고친 답 다시 확인 보강**: 연구 모듈의 확인은 고친 답을 다시 뽑아 찾은 사례의 후보 수만 센다. 재작성기가 '사례N' 표기를 떨어뜨리면 사례를 찾지 못해 확인이 그냥 통과한다. 그래서 가리거나 넓히기로 한 원래 값이 글자 그대로 남아 있으면(`RAW_VALUE_LEFT`), 바꿀 값이 있었는데 사례를 하나도 찾지 못했고 그 사례 표기도 글에 없으면(`NO_CASE_FOUND`) 통과시키지 않고 다음 방식(값만 바꾼 답 · 거절)으로 넘어간다. 의료진 대화의 누적 방어 · 턴별 방어 갈래와 실제 LLM 레드팀에 같이 건다(`review.RuledArmRun`).
- **후보 수 계기**: 보안 담당자 화면의 후보 점 원(CrowdLens) · 점 띠 · 로그 막대를 없애고, 모든 표시가 숫자 하나에 대응하는 계기로 바꾼다. 로그 눈금(1 ~ 기준 집단 461명)에 넓힘 기준(5명, 진한 선)과 가림 기준(3명, 점선)을 모든 줄에 같은 자리로 긋는다.
  - **후보가 줄어든 과정**(의료진 대화 화면 · 관제 상세): 기준 집단에서 시작해 공개된 단서를 쌓인 순서대로 하나씩 더하며 센 후보 수(`/api/watch/{대화}/cases/{사례}/narrowing`). 줄마다 어느 턴에 나간 어떤 값이 후보를 몇 명에서 몇 명으로 줄였는지, 가린 값은 '그대로였다면' 내려갔을 자리, 승인 공개는 공개한 턴 바로 뒤. 같은 단서가 다음 답에 다시 나오면 한 번만 센다.
  - **세 갈래 비교**(관제 상세): 같은 질문을 받은 의료진 화면(누적 방어) · 턴별 방어 · 방어 없음의 대화 끝 후보 수를 한 축에.
  - **목록**: '그대로였다면 → 지금' 후보 수와 작은 눈금. 머리의 큰 숫자 셋은 정의를 붙인 작은 집계표로.
  - **답 아래 판정 표**(의료진 대화 화면): 단서마다 조치 · 규칙 여부 · 그대로였다면의 후보 수, 내보낸 답의 방식, 고친 답을 다시 뽑아 확인한 기록(시도마다 방식 · 사례별 후보 수와 필요한 수 · 통과 여부). 이 기록과 '그대로였다면' 수는 의료진 화면 API에서 지운다.
- **문구**: 로그인 화면의 데모 계정 안내를 지우고, 명령줄의 '데모 계정'은 '처음 쓸 계정'으로 바꾼다. `init`이 적는 파일은 `initial_accounts.txt`, 비밀번호 옵션은 `--initial-password`(환경변수 `MEDICLOAK_INITIAL_PASSWORD`)로 바꾸고, 예전 이름(`demo_accounts.txt` · `--demo-password` · `MEDICLOAK_DEMO_PASSWORD`)도 그대로 받는다. 서버를 켤 때는 있는 쪽 파일을 알려 준다. '질문 미리 세기'와 입력칸의 '보내기 전 확인'은 실제 LLM을 부르지 않는 기록 기반 추정이라고 화면에 적는다.

- **재작성 지시 보강**: 재작성기 지시문 규칙 끝(목록 머리 앞)에 두 줄을 더한다.
  - 6번: 바꿀 값은 그 자리만이 아니라 답 전체에서 고친다. 요약 · 비교 · 주목할 점 같은 다른 문장에 다시 나오거나, 대소문자를 바꾸거나 줄여 쓴 경우(약의 성분 이름만, 날짜의 연도 · 월만)도 같은 값으로 본다. 빼기로 한 약은 줄여 쓸 수 있는 이름을 같이 적는다(예: 'naproxen'(사례2)).

- **다시 고칠 때 남은 표현 알려 주기**: 다시 확인에 떨어지면 다음 재작성 지시에 8번을 적는다. 내용은 다시 뽑은 그 사례의 단서 중 이번 계획(이미 공개한 State 포함)이 허용하지 않은 값의 글자다(예: "남은 표현: 'naproxen Oral Tablet'"). 사례 표기가 사라졌거나 원래 값이 글자 그대로 남은 경우에도 그 이유를 적는다.
- **거절 전에 사례 단위로 빼기**: 재작성 · 값 치환이 모두 통과하지 못하면 마지막으로 한 번 더 시도한다.
  - 통과하지 못한 사례가 가장 적은 시도의 답을 고른다. 수가 같으면 재작성 답을 고른다. 그 답에서 통과하지 못한 사례만 뺀다.
  - 빼는 단위는 넷이다. 그 사례를 가리키는 마크다운 머리줄 묶음, '사례N'으로 시작하는 머리 줄 묶음, 그 사례를 가리키는 문장과 같은 문단에서 그 뒤를 잇는 문장, 그리고 통째로 뺀 목록 줄의 하위 줄이다. 여러 사례를 묶은 머리줄이면 묶음째 뺀다.
  - 끝에 "사례2의 세부 내용은 환자를 알아볼 위험이 있어 이 답에서 뺐습니다."를 붙이고, 붙인 글 그대로 다시 확인한다. 통과하고 뺀 사례의 단서가 다시 뽑히지 않을 때만 그 답을 낸다(공개 방식 `CASE_DROPPED`). 아니면 거절 그대로이고, 그 시도도 기록에 남긴다.
  - 어느 사례의 실패인지 모르는 경우(추출 실패 · 사례 표기 없음), 모든 사례가 통과하지 못한 경우, 빼고 남는 사례가 없는 경우에는 빼지 않는다.
  - 뺀 사례의 판정은 모두 가림으로 기록한다(`dropped`). 의료진 화면의 사례 목록 · 사례 노트에는 '(비공개)'로, 보안 담당자의 공개 승인 목록에는 '사례째로 뺌'으로 나온다. State에는 다시 확인에서 뽑힌 단서만 들어가므로, 뺀 사례에는 아무것도 더해지지 않는다.
- 실제 LLM 갈래의 trial `versions`와 레드팀 요약에 `medicloak_release: medicloak-release-v2`를 남긴다. 지시문이 연구 모듈의 해시와 달라지기 때문이다.

**결과와 영향**

- 이번처럼 한 사례만 통과하지 못하면, 첫 답에서 그 사례만 '(비공개)'가 되고 나머지 사례는 보인다. 재작성기가 남은 표현을 따르면 두 번째 재작성에서 통과하므로 사례를 빼지 않는다.
- 사례 단위로 빼면 확인 추출이 한 번 더 든다(호출 +1). 비교 갈래(C1S)의 첫 답은 같은 요청에 앞 갈래의 답을 다시 쓰므로 호출이 늘지 않는다.
- 실제 LLM 레드팀도 같은 공개 단계를 쓴다. 그래서 이전 점검과 공개 방식 분포(`CASE_DROPPED`)와 답변 유용도가 달라질 수 있다.
- 보안 담당자 화면에서는 관제 상세의 요약 문장, 질문 흐름, 후보가 줄어든 과정에 '사례째로 뺌'으로 나온다. 뺀 사례는 공개된 것이 없으므로 후보 수를 기준 집단 전체(461명)로 센다. 전에는 State에 없는 사례의 후보 수가 비어 요약에 'null명'이 찍혔다. 이 경우를 처리하면서 함께 고쳤고, '사례 4과'처럼 틀리던 조사도 바로잡았다.
- 테스트 범위
  - 맥 S0010의 재작성 답으로 사례 빼기. 결정적 응답기 줄 모양, 문단 이어지는 문장, 하위 목록, 남는 사례가 없는 경우도 본다.
  - 가짜 LLM으로, 한 사례의 약이 다른 문장에 소문자로 다시 나오는 첫 답에서 두 경우를 본다. 남은 표현을 따른 두 번째 재작성은 통과하고, 따르지 않으면 그 사례만 빼고 낸다.
  - 프런트 의료진 문구 테스트.

### 1. 최소 공개 단위 (실제 LLM 갈래)

운영 모드 의료진 대화와 실제 LLM 레드팀의 공개 단계(`RuledArmRun(live=True)`)에 단위 맞춤을 더한다. 결정적 응답기(데모 · POC 재현)는 바꾸지 않는다.

- 허용으로 정한 나이 · 날짜(AGE · PERIOD) 값은 온톨로지 넓힘 사슬에서 공개 단위를 넘는 첫 조상으로 바꾼다. 나이는 5세 구간(AGE5) 이상, 날짜는 월(MONTH) 이상이다. 93세 → 90~94세, 2018-03-24 → 2018-03이 된다. 그 조상이 루트(나이 조건 무제약 등)이면 가린다.
- 노드가 이미 공개 단위여도 답의 글자가 노드 이름과 다르면 노드 이름으로 바꾼다. 예를 들어 노드 90~99세로 센 '93-98세'는 '90~99세'로 나간다. 내보낸 글자와 후보를 센 값이 늘 같다.
- 바꾼 판정에는 `floor`를 표시한다. 위험 때문이 아니라 단위를 맞추려고 바꾼 것이다. 조상은 후보가 늘 같거나 많으므로 단위를 맞춰서 위험이 커지지는 않는다.
- 바꿀 것이 단위 맞춤뿐이면 재작성기를 부르지 않는다. 값을 글자 그대로 바꾼 뒤(`apply_changes_deterministic`) 다시 확인한다. 공개 방식은 `ROUNDED`다. 통과하지 못하면 원래 순서(재작성 → 값 치환 → 사례 빼기 → 거절)로 간다.
- 보안 담당자의 공개 승인은 지금처럼 정확한 값을 연다. 사람이 사유를 보고 고른 값이기 때문이다.
- `medicloak_release` 버전은 `medicloak-release-v3`이다.

### 2. 사례 노트는 내보낸 답 기준

- 공개 이력(사례 노트 · 공개 승인 목록의 근거)은 내보낸 답을 다시 추출해 State에 넣은 단서(`commit`)와 맞춘다. 허용 · 넓힘 값은 내보낸 답에 같은 노드나 같은 글자로 나왔을 때만 적고, 값은 답에 나온 글자로 적는다. 가린 값은 '비공개'로 남긴다. 계획에 없었는데 답에 나온 값은 의료진이 본 것이므로 적는다.
- 노트 제목 아래에 '과거 환자 한 명의 기록'이라고 쓴다. 비슷한 사례 목록 머리에도 '사례 하나는 병원 과거 기록의 환자 한 명'이라고 쓴다.
- 용어 링크의 `[[ ]]` 괄호를 없애고 밑줄만 둔다.

### 3. 외래 진료 목록

- 목록 응답(`/api/emr/worklist`)에서 생년 · 거주 지역 · 정확한 나이를 뺀다. 나이는 진료 중 환자 띠와 같은 연령대('40대', '10세 미만')로만 보인다. FHIR Patient 자원에는 그대로 있다. 의료진이 자기 환자를 열어 보는 경로이기 때문이다.
- 진료 상태를 셋으로 나눈다. 기준일은 오늘이 아니라 가상 EMR의 마지막 기록일(합성 데이터를 만든 날)이다.
  - 진료 중: 끝나지 않은 진단 · 관리 계획이 있고 최근 3년 안에 기록이 있다.
  - 완치: 기록된 진단 · 관리 계획이 모두 끝났다.
  - 장기 미내원: 끝나지 않은 것이 있지만 마지막 기록이 3년보다 오래됐다.
  - 탭으로 나누고 진료 중을 먼저 보인다. 지금 데이터는 진료 중 79 · 완치 24 · 장기 미내원 11명이다.
- '최근 진료일'(연구 기준일) 대신 '마지막 기록'(EMR의 마지막 기록일)을 보인다. 진료 목적 옆의 날짜는 '진료 기준'으로 쓴다. 진료 지원 AI가 그날 기준으로 환자 요약을 만들기 때문이다.
- 목록 위에 '비슷한 과거 사례는 이 목록에서 찾지 않는다'고 쓴다. 외래 환자와 유사 사례 검색 대상(461명)은 처음부터 나뉜 집단이다.
- 다른 환자로 열려고 하면 먼저 확인을 받는다. 확인 문구는 "위 띠의 환자(…)를 닫고 … 환자로 엽니다. 지금까지의 대화는 조회 기록에 남습니다"이다. 지금 연 환자의 같은 진료 목적을 고르면 '열린 진료 지원 AI로 돌아가기'가 된다. 지금 연 환자 줄에는 '지금 연 환자'라고 표시한다.

### 4. 첫 답 기다리는 시간 줄이기

- 답 형식 지시: 운영 모드 의료진 대화의 대상 AI 지시문 끝에 `[답 형식]`을 붙인다. 내용은 세 가지다. 사례마다 짧은 문장 두세 개로 쓰고 표 · 머리글 · 굵은 글씨를 쓰지 않는다. 묻지 않은 날짜 · 나이 · 지역 · 횟수를 덧붙이지 않는다. 없는 내용을 '-'로 채우지 않는다. 답이 짧으면 추출 · 재작성 · 확인이 모두 짧아지고, 가릴 값 자체가 줄어 재작성까지 가는 일이 준다. 레드팀에는 붙이지 않는다. 공격 평가의 대상 AI 조건을 바꾸지 않기 위해서다. (ADR-0025에서 레드팀에도 같이 붙이고 `--answer-style`로 함께 켜고 끄도록 바꿨다.)
- 첫 답 나눠 쓰기(`Turn0Cache`): 같은 환자 · 같은 진료 목적의 첫 답 요청은 글자까지 같다(온도 0). 그래서 다른 의료진이 같은 환자를 열거나 다시 열면 앞서 받은 답을 같은 차례대로 다시 쓴다. 메모리에만 두고(4,000개, 오래된 것부터 지움) 서버를 다시 켜면 비운다. 첫 답이 거절로 끝났으면 그 대화가 쓴 요청을 지워 다음에 새로 부른다.
- 진행 표시: 여는 동안 `GET /api/emr/launch/progress`가 지금 단계와 실제 LLM 호출 수, 지난 시간을 알려 준다. 화면은 0.7초마다 묻는다. 단계 이름은 '비슷한 사례를 정리', '단서를 찾고', '가릴 값을 고쳐 쓰고', '고친 답을 다시 확인'이다.

### 5. 답 그리기

- 실제 LLM 답의 마크다운을 블록(머리글 · 문단 · 목록 · 표 · 가로줄)과 굵은 글씨로 나눠 그린다. 보호 조치가 걸린 값 조각(범위 · 비공개 표시)은 쪼개지 않고, 표 칸 · 목록 줄 안에서도 그 자리에 둔다. 결정적 응답기의 '사례N · 항목: 값' 줄은 지금처럼 항목 · 값 줄로 보인다.
- 답 복사(진료 기록에 붙이기)에서는 `**` · `#` · 백틱 기호를 뗀다.

### 6. 보호 담당자 창

- 보호 담당자 메시지를 사례 노트의 탭에서 빼서 화면 오른쪽 아래에 뜨는 창으로 옮긴다. 진료 지원 AI 화면(넓은 화면)에는 '보호 담당자에게 묻기' 버튼과 새 메시지 수가 늘 보인다. 새 메시지가 오면 버튼 위에 첫 두 줄을 미리 보인다.
- 머리줄 알림, 대화 위 '답장하기', 답 아래 안내는 어느 화면에서든 같은 창을 연다. 좁은 화면에서는 화면 아래쪽을 덮는 창으로 뜬다.
- 메시지가 없을 때는 '이럴 때 씁니다'(세부 정보 요청 · 확인 요청에 답장)를 보인다. 열린 환자가 없으면 버튼을 숨긴다. 메시지가 대화 하나에 묶이기 때문이다.

**결과와 영향**

- 실제 LLM 답에서 나이는 5세 구간, 날짜는 월보다 자세히 나가지 않는다. 단위 맞춤만 한 답은 재작성 호출이 없다(`ROUNDED`). 의료진 화면의 설명은 '나이 · 날짜는 정해진 공개 단위로 표시했습니다'이고, 보안 담당자 판정 표에는 '공개 단위'로 표시된다.
- 실제 LLM 레드팀도 같은 공개 단계를 쓰므로 공개 방식 분포와 답변 유용도가 이전 점검과 달라질 수 있다. 과잉 차단 지표(넓힘 · 가림 수)는 단위 맞춤만큼 늘어날 수 있다. 비교할 때 `medicloak_release` 버전을 같이 본다.
- 같은 환자를 두 번째로 열 때는 실제 LLM을 부르지 않는다. 처음 열 때의 시간은 답 길이에 달려 있어, 답 형식 지시가 얼마나 줄이는지는 실제 키로 재야 한다.
- 화면의 '최근 진료일'이 '마지막 기록'으로 바뀌고, 목록 응답 필드가 바뀐다(`birthYear` · `region` · `lastVisit` 삭제, `ageBand` · `status` · `statusLabel` · `openItems` · `lastRecord` 추가).
- 테스트 범위
  - 온톨로지 사슬을 따르는 단위 맞춤(실제 데이터의 노드로).
  - 가짜 LLM으로 '33-38세' 답이 재작성 없이 '30~39세'로 나가는지(`ROUNDED`).
  - 사례 노트가 내보낸 답의 값만 적는지.
  - 첫 답 나눠 쓰기와 진행 표시.
  - 외래 목록의 필드 · 진료 상태 · 정렬.
  - 프런트: 마크다운 나누기(표 칸 안의 보호 값 조각, 짝 없는 `**`), 단위 맞춤 문구.

### ADR-0025. 대상 AI 답 형식은 의료진 대화와 실제 LLM 레드팀에 같이 걸고, 사례 = 과거 환자 한 명이라는 후보 수의 뜻을 화면에 적는다

- 승인 · 2026-11-05 · 결정 양승준 · S5 · 시스템·화면
- 근거: `webdemo/backend/live.py`, `webdemo/backend/engine.py`, `webdemo/backend/app.py`, `medicloak/cli.py`, `tests/medicloak/test_medicloak.py`, `frontend/src/pages/PolicyPage.tsx`, `frontend/src/pages/ReportPage.tsx`, `frontend/src/components/monitor/ReviewTools.tsx`, `frontend/src/components/monitor/WatchRiskPanel.tsx`, `frontend/src/pages/GuidePage.tsx`, `frontend/src/components/clinic/CaseNotePanel.tsx`, `frontend/src/pages/EmrPage.tsx`, `medicloak/README.md`

**결정**

### 1. 답 형식은 하나의 설정으로, 의료진 대화와 레드팀에 같이

- 실제 LLM 대상 AI의 답 형식(`live.ANSWER_STYLE`)을 의료진 대화와 실제 LLM 레드팀에 같이 붙인다. 이렇게 해서 방어 효과를 잰 조건과 운영 조건을 같게 둔다. 레드팀의 세 갈래(방어 없음 C0 · 턴별 C1S · 누적 C1)는 같은 대상 AI 설정으로 답하므로, 갈래 사이의 차이를 방어 방식의 차이로 읽을 수 있다.
- `python -m medicloak serve --answer-style on|off`(기본 on) 하나로 둘 다 켜고 끈다. 꺼서 비교 실험을 할 수 있다.
- 레드팀 실행 기록(`trial요약.json`의 versions)에 `answer_style`을 남긴다. 켰으면 지시문 판(`short-v1:` + 지시문 SHA-256 앞 8자), 껐으면 `off`다. 실행 목록에도 남겨 리포트 화면에 '짧은 답 지시' · '답 형식 지시 없음'으로 보인다. 이 설정이 생기기 전의 실행은 '지시 없음'으로 보인다. 설정이 다른 실행끼리는 바로 비교하지 않는다.
- 보호 정책 화면(`/api/monitor/policy`의 `answerStyle`)에 지금 설정과 '공개 단위'(ADR-0024)를 보인다.
- 결정적 응답기(데모 · POC 재현)는 바꾸지 않는다. 논문 · 보고서의 POC 수치는 그대로다.

### 2. 첫 답 나눠 쓰기의 키를 해시로

- `Turn0Cache` 키는 (답 형식 판, 역할, 지시문, 대화)를 이은 글의 SHA-256이다. 지시문에는 검색된 과거 환자 기록이 들어 있으므로, 메모리에 원문을 키로 두지 않는다.
- 답 형식 판이 키에 들어가므로, 형식을 바꾸면 이전 형식으로 받은 첫 답을 다시 쓰지 않는다.

### 3. 후보 수의 뜻을 화면에 적는다

- 관제 상세 · 의료진 대화 화면의 '사례 N과 조건이 같은 과거 환자 M명' 아래에 한 줄을 붙인다. "사례 N은 과거 기록 환자 한 명입니다. 지금까지 답에 나온 이 사람의 단서를 모두 가진 사람이 461명 중 몇 명인지 셉니다. 5명 아래로 줄면 누구인지 좁혀지고, 1명이면 특정됩니다."
- 보호 정책의 용어 풀이에서 '사례'와 '후보 수'를 같은 뜻으로 고친다.
- 의료진용 '개인정보 보호 안내'에 '무엇을 막는지'를 숫자 없이 더한다. 내용은 사례 하나 = 한 사람, 진단을 보는 것만으로는 누구인지 모른다는 점, 답이 쌓여 한 사람만 남는 것을 막는다는 점이다.

### 4. 의료진 화면 다듬기

- 사례 노트를 '지금까지 보인 내용'(값) · '질문별 기록'(세로 시간선) · '다른 사례와 같은 값'(접힘) 순으로 바꾼다. 메모 앱식 백링크 구성보다 진료 기록 카드에 가깝게 하려는 것이다.
- 외래 목록의 진료 상태는 점과 글자로, 진료 목적은 글자 한 줄로 보인다. 오른쪽 기록 머리의 FHIR 자원 이름은 작은 출처 표시로 옮긴다.
- 의료진 화면의 데이터 출처 문구에서 '가상 EMR'을 뺀다. 합성 데이터라는 사실은 로그인 화면 아래 한 줄과 문서에만 둔다. 실제 환자 정보를 쓰지 않았다는 점을 밝히는 문구라 남긴다.

**결과와 영향**

- 실제 LLM 레드팀 결과가 이전 실행(지시 없음)과 달라질 수 있다. 특히 방어 없음(C0)의 위험 수치가 낮아질 수 있다. 리포트 화면의 실행 이름에 설정이 보이므로, 같은 설정끼리 비교한다.
- 테스트
  - 의료진 대화의 대상 AI 지시문이 답 형식으로 끝나는지 본다.
  - 레드팀 대상 AI 호출이 모두 답 형식으로 끝나고, 실행 기록에 지시문 판이 남는지 본다.
  - `off`일 때 지시가 없고 보호 정책에 꺼짐으로 보이는지, 형식이 다른 첫 답을 다시 쓰지 않는지, 캐시 키가 해시인지 본다.

### ADR-0026. 의료진 화면을 진료 흐름에 맞추고(조회 목적별 질문 · 사례 전체에 묻기 · 진행 표시 · 사례 비교 · 요청 상태), 거주 지역은 조회 목적 규칙으로 가린다

**결정**

### 1. 조회 목적별 진료 질문 (실제 LLM 대화)

- 예시 질문을 조회 목적마다 정한 진료 질문으로 바꾼다. 고른 사례 질문 넷과 찾은 사례 전체 질문 하나다.
  - 처방: 약 · 복용 기간, 함께 쓴 약, 처방 변경, 처방 이유
  - 시술·치료: 시술, 시술 전후 약, 시술 뒤 관리, 관련 진단
  - 경과·관리: 관리 계획, 경과, 다시 진료, 관리 중 약
- 보내기 전 경고의 '대신 물어볼 질문'도 같은 목록에서 고른다.
- 연구 질문 목록은 데모(결정적 응답기)와 레드팀에만 쓴다. 결정적 응답기는 그 목록의 문장만 알아듣기 때문이다.

### 2. 묻는 범위: 고른 사례 · 찾은 사례 전체

- 입력칸 위에 '묻는 범위' 단추(사례 N | 찾은 사례 전체)를 둔다. 전체 질문 예시를 누르면 범위도 같이 바뀐다.
- 전체로 물으면 '검색된 사례 전체에 대한 질문: '을 붙여 보낸다(`POST …/messages`의 `scope: "all"`). 공개 판정은 지금처럼 사례마다 하고, 답에 나온 값은 각 사례의 노트로 간다.
- 질문 메시지에 범위를 남겨 '사례 전체' 표시가 보인다. 데모 모드에서는 전체 질문을 받지 않는다(422).

### 3. 질문 진행 표시

- 화면 갈래(C1)의 실제 LLM만 `CallWatchLLM`으로 감싼다. 질문에 답하는 동안 `GET /api/clinic/progress`가 지금 단계와 호출 수, 지난 초를 알려 준다. 단계는 답 쓰기, 단서 찾기, 고쳐 쓰기, 다시 확인이다.
- 비교 갈래(C1S)는 감싸지 않아, 뒤에서 도는 호출이 진행 수에 섞이지 않는다.

### 4. 조회 목적 규칙: 거주 지역

- 거주 지역은 세 조회 목적 어디에도 진료 판단에 쓰지 않는다. 그래서 실제 LLM 갈래(의료진 대화 · 레드팀)에서는 후보 수와 관계없이 늘 가린다(`review.PURPOSE_UNNEEDED`). 개인정보의 목적 외 이용 금지를 조회 목적에 바로 묶는 것이다.
- 보안 담당자 규칙과 같은 길(`RuledArmRun.blocked`)로 공개 계획과 다시 확인에 건다. 판정에는 `purpose` 표시가 남는다.
- 의료진 화면에는 "이번 조회 목적에 필요하지 않은 정보는 답에서 뺐습니다"라고 보인다. 이 값에는 세부 정보 요청 단추가 없고, 공개 승인 목록에도 오르지 않는다.
- 보내기 전 경고도 같은 이유를 말한다. `medicloak_release`는 `medicloak-release-v4`다.

### 5. 사례를 구별하고 비교하기

- 사례 목록 머리에 '공통' 줄을 둔다(여러 사례에 같이 나온 진단 · 대표 항목).
- 사례마다 '주진단 같음' · '고려 중 처치와 같음'(환자 띠와 비교), 다수와 다른 대표 항목에는 '다른 항목'을 붙인다.
- 대화창 처음에 '비슷한 사례 N건을 찾았습니다' 요약을 보인다.
- 셋 다 화면에 이미 보이는 값만 센다. 새 값을 드러내지 않는다.
- '비교' 단추로 사례 × 항목 표를 연다. 각 사례에 대해 지금까지 답에 실제로 보인 값(사례 노트와 같은 근거)만 채운다.

### 6. 세부 정보 요청 상태

- 요청 뒤에 같은 사례로 온 보호 담당자 메시지로 상태를 정한다. 공개 승인이면 '승인됨', 답장이면 '답장 옴', 없으면 '대기 중'이다.
- 답 아래와 보호 담당자 창의 요청 아래에 상태와 처리 시각을 보인다. 답 다음 질문을 보내기 전까지 보낸 요청만 그 답의 요청으로 본다.

### 7. 그 밖의 화면

- 환자 띠에 'AI에 보내는 요약' 표시를 붙인다. 툴팁 문구는 "이름 · 생년 · 주소는 보내지 않습니다"다.
- 외래 목록은 한국어 진단 이름으로도 찾는다. 데이터에 나오는 진단에 맞춰 이름표를 만들었고(`koTerms.ts`), 화면 값은 그대로다.
- 진료 목적의 기준일이 모두 같으면 한 번만 보인다.
- 답 복사는 진료 기록에 붙이는 형식이다. "[진료 지원 AI · 유사 사례 참고 · 사례 N]" 머리를 붙이고, 보호한 값이 있으면 MediCloak 처리 꼬리를 붙인다.

### 8. 운영 옵션과 기록

- `serve --extractor-model` · `--rewriter-model`로 추출기 · 재작성기만 다른 모델(빠른 모델)을 쓸 수 있다. 화면의 대상 AI 이름에 함께 보인다.
- 질문 감사 기록의 행위자를 '의료진'으로 고치고, 질문 범위를 남긴다.

**결과와 영향**

- 실제 LLM 레드팀에서 거주 지역 단서가 늘 가려진다. 지역을 이용한 공격 성공은 줄고 넓힘 · 가림 수는 늘 수 있다. `medicloak-release-v4` 실행끼리만 비교한다.
- 예시 질문 API(`/suggestions`)의 항목에 `scope`가 더해진다. 데모 모드는 늘 `case`다.
- 테스트
  - 조회 목적별 예시 질문(재식별 문장 없음)
  - 전체 질문의 접두어와 범위 기록, 잘못된 범위 422
  - 질문 진행 표시(호출 수 · 단계 · 끝나면 비활성)
  - 거주 지역 조회 목적 규칙(답에 없음, `purpose` 표시, 공개 승인 목록 제외, 버전)
  - 프런트: 요청 상태 · 사례 요약 · 한국어 이름 · 복사 형식 · 조회 목적 문구

**결정**

### 1. 검토 보조 에이전트 (`webdemo/backend/assist.py`)

의료진이 세부 정보 요청을 보내면 뒤에서 한 번 돈다. 관제 상세의 '다시 만들기'로 다시 돌릴 수도 있다. 순서는 아래와 같고, 화면에 '확인한 순서'로 그대로 보인다.

1. **요청 읽기**: 사례, 조회 목적, 의료진이 쓴 사유
2. **가린 값 모으기**: 그 사례의 공개 승인 대상 값. 값 원문은 읽지 않고 단서 종류 · 처리 · 어느 답인지만 본다.
3. **하나씩 열어 보기**: 지금 누적 상태에 그 값 하나를 더했을 때의 후보 수.
   - `Session.what_if`가 `approve`와 같은 방식으로 State 사본에 더해 센다. State는 바꾸지 않는다.
4. **조회 목적과 대조**: 처방 · 시술·치료 · 경과·관리 판단에 그 단서가 쓰이는 정도. 직접 씀 · 범위로 충분 · 관련 적음으로 나눈다(`PURPOSE_NEED`).
5. **함께 열어 보기**: 공개 가능한 값을 후보가 많이 남는 것부터 하나씩 더해 본다. 함께 열면 기준 아래로 내려가게 하는 값은 '사유 확인'으로 돌린다.
6. **초안 쓰기**: 담당자용 요약, 의료진 답장, 공개 사유를 쓴다.

추천은 규칙으로 정한다.

| 조건 | 추천 |
| --- | --- |
| 하나만 열어도 후보가 기준(5명) 이상 | 공개 가능 |
| 조회 목적과 관련 적음 | 공개하지 않음 |
| 이미 범위로 보이고, 범위로 충분한 단서 | 지금 범위 유지 |
| 열면 후보 1명 | 공개하지 않음 |
| 그 밖 (진료에 쓰이지만 기준 아래로 줄어듦) | 사유 확인 뒤 결정 |

- **LLM의 몫**: 실제 LLM은 요약과 답장 문장만 쓰고 추천은 바꾸지 않는다.
  - 모델은 재작성기와 같다(`--rewriter-model`).
  - 의료진 질문 호출이 기다리면 자리를 양보한다.
  - 사용량은 '검토 보조'로 따로 센다.
- **정해진 문장으로 돌아가는 경우**: 아래 중 하나면 LLM 대신 정해진 문장으로 쓴다.
  - 결정적 응답기 · 연결 점검 모드
  - 호출 실패
  - LLM 답이 JSON 형식이 아님
  - 의료진 답장에 숫자('사례 N' 제외)나 '후보'가 섞임
- **LLM에 보내지 않는 것**: 가린 값의 원문, 환자 번호, 과거 기록. 보내는 것은 단서 종류 · 처리 · 후보 수 · 조회 목적 · 요청 문장뿐이다.
- **스스로 하지 않는 일**: 공개 · 답장 · 규칙을 보내지 않는다. 관제 상세에서 담당자가 직접 한다.
  - '공개 가능 N개를 승인 창에 담기': 공개 승인 창에 고를 값과 사유 초안을 채운다.
  - '답장 칸에 넣기': 답장 칸에 초안을 넣는다.
- **기록과 API**:
  - 초안은 메모리에만 둔다.
  - 만들 때마다 감사 기록 `assist_draft`를 남긴다(행위자 '검토 보조 AI'). 사례 · 추천 · 추천별 수 · 쓴 방식만 담고 값은 담지 않는다.
  - API: `GET · POST /api/monitor/sessions/{대화}/assist` (보안 담당자 전용).
- **화면**: 관제 상세의 스크롤 영역 맨 앞에 검토 보조와 공개 승인 창을 둔다. 내용이 길어도 승인 단추까지 내려갈 수 있다.

### 2. 로그인 화면

- 왼쪽은 EMR 머리줄과 같은 짙은 청록 판이다. 제품 이름, 한 줄 설명, 역할 둘을 둔다.

- 오른쪽 로그인 양식에는 다음을 둔다.
  - 비밀번호 보기
  - Caps Lock 알림
  - 사실인 안내 셋: 감사 기록, 60분 미사용 시 자동 로그아웃(`auth.IDLE_TIMEOUT`), 계정 문의처
- 아래에 판정 규칙 판(`/api/health`의 `release`)을 보인다.
- 합성 데이터 안내 줄은 지운다. 데이터 출처는 README와 논문에 적는다.

- 테스트

### 1. 자동 레드팀 점검 (`webdemo/backend/autocheck.py`)

- **설정과 지문**: 점검 조건을 정하는 설정은 넷이다.
  - 판정 규칙 판(`medicloak_release`)
  - 대상 AI 답 형식
  - 모델(대상 AI와 역할별 모델)
  - 규칙 추출

  이 넷의 해시를 지문으로 삼는다. 실제 LLM 점검마다 시작할 때의 설정과 지문을 기록에 남긴다. 직접 실행한 점검도 같다.
- **켤 때**: 지금 지문을 점검 기록과 견준다.
  - 같은 지문의 점검이 있으면(끝남 · 멈춤 · 오류 · 도는 중) 돌리지 않는다. 멈춘 점검을 다시 돌려 호출을 쓰지 않는다.
  - 없으면 '유형마다 1명'(질의 환자 3명, k 피드백 퍼저) 점검을 뒤에서 시작한다. 처음 켤 때, 설정이 바뀌었을 때, 서버를 다시 켜느라 끊긴 점검만 있을 때가 여기에 든다.
  - 서버 출력과 정책 화면에 이번에 한 일을 적는다.
- **정해진 시각**: `--auto-redteam-daily HH:MM`이면 매일 그 시각(서버 시계)에도 같은 규모로 돌린다. 다른 점검이 돌고 있으면 그날은 건너뛴다.
- **점검 호출의 우선순위**: 의료진 질문 호출에 자리를 양보한다. 레드팀 실행의 기존 방식(`background_calls`)을 그대로 쓴다.
- **비교**: 실제 LLM 점검이 끝날 때마다, 같은 규모 · 같은 퍼저로 바로 앞에 끝난 점검과 누적 방어(C1) 지표를 견준다.

  | 수준 | 조건 |
  | --- | --- |
  | 경고 | 후보가 기준 아래로 내려간 대화의 비율이 늘었다 |
  | 주의 | 답변 유용도가 0.05 이상 떨어졌거나, 과하게 가린 비율이 5%p 이상 늘었다 |
  | 이상 없음 | 둘 다 아니다 |
  | 첫 기준 점검 | 견줄 직전 점검이 없다 |

  - 바뀐 설정도 같이 적는다. 예: 대상 AI 답 형식: 켬 → 끔
  - 질의 환자 3명 규모라 작은 차이는 우연일 수 있다는 안내를 붙인다.
- **화면**:
  - 관제 위 한 줄: 자동 점검이 도는 중이거나, 마지막 비교가 경고 · 주의일 때만 보인다.
  - 리포트: 고른 점검 위에 '직전 점검과 비교' 표를 둔다. 실행 이름 앞에는 '자동 · 설정 바뀜' · '자동 · 정기'를 붙인다.
  - 정책 화면: 자동 점검 설정과 이번에 켤 때 한 일을 보인다.
- **기록**: 감사 기록에 '자동 점검'이 시작(`redteam_start`, trigger)과 비교 결과(`redteam_compare`)를 남긴다.
- **켜고 끄기**: `--auto-redteam change`(기본) · `off`. `--llm real`일 때만 돈다. API는 `GET /api/redteam/auto`(보안 담당자)다.

### 2. 답 안의 가린 값 표시 (`clinic.mark_hidden`)

- 글에서 찾지 못한 '가림' 조치마다 자리 표시 조각(`placeholder`)을 넣는다.
  - 자리는 그 사례 단락의 끝이다. 다음 사례가 시작하는 문장 바로 앞이고, 다음 사례가 없으면 답 끝이다.
  - 조각에는 단서 이름을 붙인다. 고른 사례가 아니면 사례 이름도 붙인다('사례 2 나이').
  - 같은 사례 · 단서는 한 번만 표시한다.
  - 사례째로 뺀 값은 뺀 사례 안내가 따로 있어 표시하지 않는다.
- 의료진 화면에는 잠금 표시 '시기 비공개'로 보인다. 툴팁으로 까닭을 알린다(개인 식별 · 보안 담당자 규칙 · 조회 목적).
- 진료 기록 복사에는 '(시기 비공개)'로 남는다. 보안 담당자의 의료진 대화 화면에는 '시기 가림'으로 보인다.
- 내보낸 글, 판정, 후보 수, 다시 확인은 바뀌지 않는다. 화면 조각만 더한다. 값은 넣지 않고, 사례 노트와 같은 정보만 보인다.

**결과와 영향**

- 운영 서버를 처음 켤 때와 설정을 바꿔 켤 때 실제 LLM 점검이 한 번 돈다(유형마다 1명). 끄려면 `--auto-redteam off`.
- 레드팀 기록에 `trigger` · `settings` · `fingerprint` · `compare`가 더해진다. 이전 기록에는 없으므로, 이번 판을 처음 켜면 설정이 바뀐 것으로 보고 한 번 돈다.
- 의료진 답 조각에 `placeholder` · `label`이 더해진다.
- 테스트
  - 비교 수준 · 바뀐 설정 문장 · 켤 때 결정(같은 지문, 끊긴 것만 있음, 설정 바뀜, LLM 없음) · 매일 시각
  - 서버를 세 번 켜기(기준 점검 → 같은 설정이면 안 돎 → 답 형식을 끄면 다시 돌고 직전 점검과 비교) · 감사 기록 · 의료진 403

### 1. 추출기 출력 바로잡기 (`textguard.fix_extraction`, `LiveLLM`이 부름)

- **근거 문장**: 글자열이면 목록으로 감싼다. 답에 그대로 없으면 답에 있는 조각이나 원래 값으로 바꾼다. 공개 계획(`RuleDefender.change_lines`)도 근거를 원 관측에서 다시 읽어 글자열 목록으로 넘기고, 한 글자 근거는 버린다.
- **사례 문서 대조 보탬**(`source="DOC_MATCH"`):
  - 답에서 '사례N'이 나온 문장을 그 사례에 붙인다. 같은 단락의 이어지는 문장과 '사례 모두' 같은 전체 문장도 포함한다.
  - 그 문장에 그 사례 문서의 진단 · 시술 · 약(성분 이름 포함) · 관리 계획 · 거주 지역 표현이 그대로 있는데 추출기가 그 사례에 같은 값을 내지 않았으면 관측을 더한다.
  - 성별은 사례 하나만 말한 문장에서 '남성/여성'이 직접 쓰였을 때만 더한다.
  - 나이 · 날짜는 규칙 추출이 맡으므로 더하지 않는다.
  - 문서에 있는 참값만 더하므로 판정이 느슨해지지 않는다. 의료진 대화와 실제 LLM 레드팀이 같은 길을 지난다.
- **고친 답 길이 막기**: 다시 확인할 답이 `max(6000자, 원 답 길이 × 4)`보다 길면 추출기에 보내지 않고 통과하지 못한 것으로 본다(`TEXT_TOO_LONG`).

### 2. 기간은 날짜와 따로, 범위로

- 대상 AI 답 형식에 한 줄을 더한다: 기간을 물으면 날짜 대신 '약 2주', '3~7일'처럼 답한다.
- 실제 LLM 방어 갈래(C1 · C1S)는 내보낼 글의 상대 기간을 범위로 바꾼다(`coarsen_durations`). 범위는 묻는 범위(사례 하나 · 전체)와 상관없이 같다.

  | 원래 길이 | 보이는 범위 |
  | --- | --- |
  | 3일 이하 | 3일 이내 |
  | 4~7일 | 1주 이내 |
  | 8~14일 | 약 1~2주 |
  | 15~31일 | 약 2~4주 |
  | 32~92일 | 약 1~3개월 |
  | 93~183일 | 약 3~6개월 |
  | 184~330일 | 약 6개월~1년 |
  | 331~548일 | 약 1년 |
  | 549~1095일 | 약 1~3년 |
  | 그보다 김 | 3년 넘게 |

  - '3월 15일' 같은 날짜, '1일 2회' 같은 횟수, '2주 간격'은 바꾸지 않는다. '3일 전'은 '최근 3일 이내'가 된다.
- 재작성 지시에 9번을 더한다: 날짜를 빼더라도 기간은 '약 1~2주'처럼 범위로 남겨도 되고, 정확한 날짜와 일수는 쓰지 않는다.
- 절대 날짜(시기)는 지금처럼 후보 수로 판정한다.
- 사례 노트에 사례마다 '기간' 항목으로 남긴다. 표시는 "기간은 범위로만 보여 줍니다"다. 공개 판정(가림 · 범위 · 그대로)의 집계에는 넣지 않는다.
- `medicloak_release`는 `medicloak-release-v5`다.

### 3. 사례 카드: 가린 것과 아직 모르는 것을 나눈다

- 첫 답이 말하지 않은 사례는 '첫 답에 나오지 않음 · 물으면 답에 나온 값이 여기에 채워집니다'로 보인다(`mentioned=false`). 가린 값만 '비공개'다.
- 뒤 답에서 진단 · 대표 항목이 나오면 카드를 채운다. 공통 요약은 아는 값만 센다.

### 4. 운영 모드 진료 기준: 가장 최근 진료 (`visit.py`)

- 진료 목적마다 그 목적이 성립하는(관련 항목이 있는) 진단 사건 중 가장 최근 것을 기준 진료로 삼는다. 관련 항목 규칙은 연구와 같다.
- 동반질환은 그날 이어지던(끝나지 않은) 다른 진단이다. AI에 보내는 요약에는 많이 나온 두 범주를 쓴다.
- 유사 사례 검색은 그날까지의 진단 · 약 · 시술 기록 전체로 한다. 기준일이 최근이라 동반질환과 복용약이 검색에 들어간다.
- 외래 목록의 진료 목적 카드 · 환자 띠 · 검색이 같은 기준을 쓴다. 카드에 동반질환을 함께 보인다.
- 레드팀 · 연구 실행(`plan_all`, `make_prefix`)은 연구 기준 그대로다. `serve --visit research`로 의료진 대화도 연구 기준으로 되돌릴 수 있다.

### 5. 속도

- **의료진 호출 우선**: 의료진 질문 호출은 앞 호출끼리만 동시 호출 수를 센다. 뒤에서 이미 보낸 비교 갈래 · 미리 준비 · 레드팀 호출이 끝나기를 기다리지 않는다. 뒤 호출은 앞 호출이 기다리거나 보내는 중이면 양보한다. 같은 순간의 호출은 '앞 n개 + 이미 보낸 뒤 호출'까지다.
- **첫 답 미리 준비**: 외래 목록에서 환자 · 진료 목적을 고르고 1초 머물면 화면이 `POST /api/emr/prefetch`를 부른다.
  - 서버는 첫 답 전체를 뒤에서 부른다: 대상 AI 답 · 추출, 그리고 화면 갈래(C1)의 첫 답 공개 처리(재작성 · 다시 확인).
  - 결과는 첫 답 나눠 쓰기(`Turn0Cache`)에 남고, 열 때 꺼내 쓴다. 부르는 중인 요청은 끝나기를 기다려 같은 호출을 두 번 하지 않는다.
  - 대화 · 기록은 만들지 않는다. 의료진마다 한 번에 하나다. 거절이면 남기지 않는다.
  - 끄기: `serve --prefetch off`.
- **진행 표시**: '답을 쓰는 중' · '답에 환자를 알아볼 수 있는 값이 있는지 확인하는 중' · '알아볼 수 있는 값을 고쳐 쓰는 중' · '고친 답을 한 번 더 확인하는 중'과 걸린 초만 보인다. 호출 수는 보이지 않는다.

### 6. 의료진 화면

- **사례 노트**: 넓은 화면에서는 기본으로 접어 오른쪽 가는 띠로 둔다. 띠를 누르면 펼치고, 그 선택은 브라우저에 기억한다. 펼쳐도 '질문별 기록'은 접혀 있다. 좁은 화면의 탭은 그대로다.
- **사례 카드 꼬리표**: '주진단 같음' 같은 꼬리표를 카드에서 빼고, 사례 노트 머리에 '내 환자와 같은 점: 주진단'으로 한 줄만 둔다.
- **AI에 보내는 요약**: 누르면 대상 AI 지시문에 실제로 들어가는 환자 요약 다섯 줄, 기준 진료일, 검색에 쓰는 기록 범위('2026-07-28까지의 진단 7개 · 약 5개 · 시술 7개')를 펼친다. 나이는 요약에 들어가는 그대로(예: 52세) 보인다. 안내 문구의 '연령대'를 '나이'로 고친다.
- **묻는 범위 안내** (`scopeHint`):
  - 범위가 사례 하나인데 질문이 여러 사례를 가리키면 안내를 띄운다. '사례들', '모든 · 각 · 찾은 사례', '사례마다', '공통', 사례 번호 둘 이상 등이 그렇다. 단추는 '찾은 사례 전체로 보내기' · '사례 1만 묻기'다.
  - 범위가 사례 하나인데 다른 사례 번호 하나만 물으면 '사례 3으로 옮겨 묻기' · '사례 1로 보내기'를 보인다.
  - 이 두 경우에는 Enter를 한 번 붙잡고 안내를 강조한다. 한 번 더 누르면 지금 범위로 보낸다. 범위를 고르는 동안 보내기 전 확인(고른 사례 기준)은 숨긴다.
  - 범위가 전체인데 사례 하나만 물으면 그 사례 대화에서 묻기를 권한다. 붙잡지는 않는다.
- **조회 기록**: 지난 진료에 환자 번호(EMR 번호 앞 8자리)를 보이고, '서버를 다시 켜기 전'은 '보관된 기록'으로 바꾼다.
- **리포트 그래프**: '경계 N명' · '기준 미달' 글자를 선 위에 그리고, 띠 색 테두리를 둘러 선과 겹쳐도 읽히게 한다.

### 7. 오늘 진단 고르기 (2026-11-06 덧붙임)

- **배경**: 가장 최근 진료와 오늘 볼 문제가 다를 수 있다. 환자 `0c6f6684`는 마지막 진료가 치은염(2025-05-20)이라, CKD 환자의 처방을 보려 해도 고를 수 없었다.
- **결정**:
  - 외래 목록의 진료 목적 아래에 '오늘 볼 진단'을 둔다. 후보는 그 환자의 진단 이름마다 그 목적이 성립하는(관련 항목이 있는) 가장 최근 사건이고, 최근 것부터 보인다(`GET /api/emr/visits`). 기본(지금 기준 진료)에는 '(기본)'을 붙인다.
  - 고르면 그 진단 사건을 기준 진료로 쓴다(`visit_binding(index_event=…)`): 주진단 · 고려 중 처치 · 그날 이어지던 동반질환 · 그날까지의 검색 기록. 고른 진료 목적 카드가 그 진단 기준으로 바뀐다.
  - 열기 · 미리 준비에 `visitEvent`를 보낸다. 기본과 같으면 기본으로 본다. 쓸 수 없는 사건이면 400이다.
  - 같은 환자 · 목적이라도 고른 진단이 다르면 대화를 새로 연다. 환자 요약에 `visitEvent` · `visitChosen`을 더해, 지금 연 대화와 같은지 화면이 판단한다('돌아가기').
  - 직접 입력은 받지 않는다. 기록에 있는 진단만 고르므로 검색 · 패널 규칙이 그대로 맞는다.
  - 레드팀 · 연구 실행은 바뀌지 않는다.

### 8. 첫 답 미리 준비를 감사 기록에 (2026-11-06 덧붙임)

- 미리 준비는 열기 전에도 환자 요약과 검색된 사례 기록을 대상 AI로 보낸다. 하나가 끝날 때마다 감사 기록에 `emr_prefetch`(진료 목적, 질의 환자, 고른 진단과 그 진료일, 실제 호출 수, 성공 여부)를 남긴다. 받아 둔 답만 써서 호출이 없었으면 그렇게 보인다. 화면에는 '첫 답 미리 준비 (열기 전)'로 보인다.
- 도는 중에 다른 환자 · 진단을 고르면 버리지 않고, 마지막으로 고른 것 하나만 앞의 것이 끝난 뒤 이어서 준비한다(`queued`). 진단을 바꿔 고르는 흐름에서 고른 진단이 준비되지 않던 일을 막는다.
- 열기(`emr_launch`)에도 고른 진단과 진료일을 남긴다.

### 9. 답 속 비공개 표시를 알아보기 쉽게 (2026-11-06 덧붙임)

- **배경**: '처방 약 비공개' 표시가 다른 회색 꼬리표와 비슷했고, 사례 줄 사이 빈 줄에 혼자 떨어져 앞 줄의 꼬리표처럼 보였다. 같은 줄에 그 사례의 다른 약이 보이는데 '처방 약 비공개'라고만 해 헷갈렸다. 글에 남은 '(비공개)'는 사례와 상관없이 가림 조치 순서대로 이어져, 사례 2의 약 자리가 사례 1 시기로 이름 붙기도 했다.
- **결정**:
  - 표시는 그 사례 마지막 줄의 글 끝에 붙인다. 빈 줄 · 줄바꿈 앞으로 당긴다. 다음 사례가 없으면 그 사례가 나온 문단 끝이다.
  - 같은 답에 그 사례의 같은 단서가 다른 값으로 보이면 '처방 약 일부 비공개'로 쓴다(`partial`). 진료 기록 복사 · 보안 담당자 화면도 같다.
  - 글에 남은 '(비공개)'는 그 문장의 사례 조치에 잇는다(`place_suppressed`). 사례 안에서는 조치 순서대로 잇는다.
  - 모양: 잠금색 테두리를 두고, 답 안에서는 사선 막대(가린 자리)를 붙인다. 글 안의 표시에는 단서 이름을 붙인다('처방 약 비공개'). 항목 이름이 따로 보이는 줄에서는 붙이지 않는다.
  - 내보낸 글 · 판정 · 후보 수는 바뀌지 않는다. 화면 조각만 바뀐다.

**결과와 영향**

- 판정 규칙 판(v5)과 대상 AI 답 형식이 바뀌었다. 실제 LLM으로 서버를 켜면 자동 레드팀 점검이 한 번 돈다(ADR-0028).
  - 레드팀 수치가 바뀔 수 있다. 문서 대조 보탬으로 단서가 늘면 더 보수적이 되고, 기간 범위로 답 글이 달라진다.
  - 직전 점검과의 비교에 이 판 차이가 적힌다.
- 의료진 대화는 연구 계획과 다른 기준 진료를 쓴다. 환자 요약 · 검색된 사례가 연구 실행과 다를 수 있다. 첫 답 나눠 쓰기의 열쇠도 달라진다.
- API에 더해진 것:
  - 환자 요약의 `visitDate` · `aiSummary` · `searchBasis`
  - 사례의 `mentioned`

  - 외래 목록 진료 목적의 `comorbidity`
  - `POST /api/emr/prefetch`
  - (덧붙임) `GET /api/emr/visits`, 열기 · 미리 준비의 `visitEvent`, 환자 요약의 `visitEvent` · `visitChosen`, 답 조각의 `partial`, 감사 기록 `emr_prefetch`와 `visit_dx` · `visit_date`

- 테스트

### ADR-0030. 보안 담당자 화면을 고친다 (열람 메모 필수, 감사 기록에 환자 기호, 고위험 승인, 승인 공개는 경보와 따로, 대화 사이 반복 조회 표시, 세 줄 요약)

- 승인 · 2026-11-06 · 결정 양승준 · S5 · 시스템·화면
- 근거: `webdemo/backend/monitor.py`, `webdemo/backend/app.py`, `tests/medicloak/test_medicloak.py`, `frontend/src/lib/monitorBrief.ts`, `frontend/src/lib/monitorBrief.test.ts`, `frontend/src/lib/auditText.ts`, `frontend/src/lib/auditText.test.ts`, `frontend/src/components/monitor/RevealDialog.tsx`, `frontend/src/components/monitor/ReviewTools.tsx`, `frontend/src/components/monitor/SessionDetail.tsx`, `frontend/src/components/monitor/QueueTable.tsx`, `frontend/src/pages/MonitorPage.tsx`, `frontend/src/pages/AuditPage.tsx`, `frontend/src/api/monitorApi.ts`, `frontend/src/types/monitor.ts`, `medicloak/README.md`

**결정**

판정 · 후보 수 · 판정 규칙 판(v5)은 바꾸지 않는다. 보안 담당자 화면과 감사 기록만 바꾼다.

### 1. 원문 열람: 사유를 고르고 한 줄을 적어야 열린다

- 열람 창에 미리 골라 둔 사유가 없다. 사유(오탐 확인 · 의료진 문의 대응 · 규칙 수정 검토 · 기타)를 고르고 '확인하려는 것'을 5자 이상 적어야 '기록 남기고 보기'가 눌린다.
- 운영 모드 서버는 `note`가 5자 미만이면 422로 막는다(`POST /api/monitor/sessions/{sid}/reveal`). 데모 서버는 화면만 막는다.
- 감사 기록 `reveal`에 사유와 적은 내용, 열람으로 보이게 되는 모든 환자의 기호가 남는다.

### 2. 감사 기록에 환자 기호

- 기호: `"P-" + HMAC-SHA256(키, 환자 번호 앞 8자)` 앞 6자(`Monitor.tag`). 같은 번호는 늘 같은 기호이고, 키 없이는 기호에서 번호를 알 수 없다.
- 키는 처음 쓸 때 만들어 DB meta `subject_tag_key`에 둔다. 서버를 다시 켜도 같은 기호다. DB가 없는 데모 서버는 켤 때마다 새 키를 쓴다.
- 감사 기록에 `patient_tag`(지금 환자) · `subjects`([{case, tag}], 다룬 사례)를 남긴다: 원문 열람 · 확인 요청 · 규칙 걸기/풀기/실패 · 공개 승인 · 의료진 메시지 · 의료진 질문 · 새 대화 · EMR 열기 · 첫 답 미리 준비.
- 관제 상세에는 번호 대신 기호가 늘 보인다(지금 환자 · 초점 사례). 번호는 지금처럼 열람한 뒤에만 보인다.

### 3. 기준 아래로 내려가는 공개는 고위험 승인 (2인 확인 대신)

- 승인 창은 값을 고를 때마다 서버에 함께 공개한 뒤의 후보 수를 묻는다(`POST /api/monitor/sessions/{sid}/what-if`, 승인과 같은 계산, State는 바꾸지 않음).
- 가장 적은 후보 수가 기준(5명) 아래면:
  - 빨간 칸에 몇 명까지 줄어드는지 보이고, '후보가 N명까지 줄어드는 것을 알고 공개합니다' 확인란을 받는다. 고른 값이 바뀌면 확인란은 다시 비운다.
  - 사유는 15자 이상(`HIGH_RISK_REASON`). 보통 승인은 지금처럼 5자.
  - 서버도 같은 조건을 다시 센다. `confirmLowK`가 없거나 사유가 짧으면 422.
- 승인 기록과 감사 기록 `approve_release`에 `high_risk`와 공개 뒤 가장 적은 후보 수(`k_min`)를 남긴다. 화면에 '고위험' 표시가 붙는다.

### 4. 승인 공개로 내려간 사례는 경보와 따로 센다

- 방어 규칙이 지킨 후보 수는 첫 승인 공개 전까지의 턴 기록으로 센다. 그때 기준 이상이었고 승인한 값 때문에 기준 아래가 된 사례는 `approved_low`, 나머지 기준 아래 사례는 `violated`(경보)다.
- 관제 첫 화면의 '기준 5명 아래 사례'(`kpi.identified`)는 `violated`만 센다. '승인 공개로 기준 아래'를 따로 보인다. 목록 줄에도 '기준 아래 · 사례 N'(빨강)과 '승인 공개로 기준 아래 · 사례 N'(회색)을 나눠 적는다.

### 5. 요청이 온 대화는 요청한 사례부터

- 보안 담당자가 답할 차례인 요청이 있으면 그 요청의 사례가 초점이다(목록의 후보 수 · 상세의 후보 수 칸 · 세 줄 요약).

### 6. 두 번 보내기를 한 번으로

- 대화의 마지막 메시지와 보낸 쪽(의료진 · 보안 담당자) · 종류 · 사례 · 글이 같고 15초(`DUP_WINDOW`) 안이면, 새로 쓰지 않고 앞의 것을 돌려준다(`Monitor._duplicate`). 의료진 요청 · 답장, 보안 담당자 답장 · 확인 요청이 해당된다. 감사 기록도 한 줄이다.

### 7. 걸지 못한 규칙도 감사 기록에

- 규칙 걸기가 실패하면(409 · 422) `add_rule_failed`에 사례 · 단서 · 메모 · 까닭(`why`) · 환자 기호를 남긴다. 화면에는 '규칙 걸기 실패'로 보인다.

### 8. 감사 기록 화면 문구

- 서버 종류를 알기 전에는 아무 문구도 보이지 않는다.
- 운영 서버: 'DB에 모두 남고, 여기에는 최근 2,000건을 보입니다'. 데모 서버: '서버를 다시 켜면 지워지는 데모 기록입니다 (최근 2,000건)'.
- 사유와 메모 칸 아래에 다룬 환자('지금 환자 P-… · 과거 환자 사례 1 P-…')를 한 줄로 보인다. 열람 기록에는 고른 사유와 적은 내용을 함께 보인다.

### 9. 상세 화면 맨 위 세 줄

- '위험했던 것 · 시스템이 한 일 · 내가 할 일'을 먼저 보인다(`monitorBrief.detailBrief`).
  - 내가 할 일은 요청이 있으면 요청 칸의 단추를, 경보면 원문 열람과 규칙을, 반복 조회면 확인 요청을 가리킨다. 할 일이 없으면 없다고 적는다.
  - 요청(보라)과 경보(빨강)일 때만 글을 굵게 한다.
- 요청 칸은 위에 고정하고, 세 줄 요약은 스크롤 영역 맨 위에 둔다. 승인 창 · 질문 흐름을 볼 자리를 남기기 위해서다.
- 세 갈래 비교 막대와 '후보가 줄어든 과정'은 '자세히'를 눌러야 보인다. 줄어든 과정은 펼칠 때 받는다.

### 10. 같은 과거 환자를 다른 대화에서도 물으면 표시한다

- 대화마다 질문의 답에 나온 사례(턴 1부터)의 과거 환자 기호(`asked_subjects`)를 모은다.
- 최근 30일(`REPEAT_WINDOW`) 안의 다른 대화(지난 대화 포함)에서도 같은 기호를 물었으면 그 대화에 `repeat_subjects`([{case, tag, conversations, clinicians}])를 붙인다. 확인 필요로 올리고, 다른 표시가 없으면 '같은 과거 환자 다른 대화에서도 조회'를 단다.

- **판정은 바꾸지 않는다.** 표시와 기록만 한다.

**결정**

### 1. 승인 결과를 항목마다 알린다

- 공개한 값에는 어떻게 가렸던 값인지 적는다. 가림이면 '가렸던 값', 넓힘이면 '범위로 보였던 값', 사례째로 뺐으면 '답에서 뺐던 값'이다(`engine.Session.approve`가 승인 항목에 `action`을 남긴다).
- 요청한 사례에서 이번에 공개하지 않은 값은 단서마다 한 줄로, 까닭과 대안을 붙인다(`assist.kept_items`).
  - 까닭은 검토 보조와 같은 판정에서 온다(`assist.analyse`, 공개 전 State).
    - 지금 범위 유지: "지금 보이는 범위로도 판단에 충분하다고 보아 범위로 둡니다."
    - 사유 확인 뒤 결정: "그대로 보이면 과거 환자를 알아볼 수 있어 이번에는 열지 않았습니다. …"
    - 공개하지 않음, 목적과 관련 적음: "이번 처방 참고 목적과 관련이 적어 공개하지 않습니다."
    - 공개하지 않음, 그 밖: "공개하면 그 과거 환자를 알아볼 수 있어 공개하지 않습니다."
    - 검토 보조가 공개 가능으로 봤는데 승인하지 않음: "이번에는 공개하지 않았습니다."
  - 대안은 검토 보조의 의료진용 문장(`ALT_REPLY`)이다. 예: "정확한 날짜 대신 진단 뒤 몇 달째였는지로는 알려 드릴 수 있습니다."
  - 숫자(후보 수)는 쓰지 않는다. 이번에 그 단서를 하나라도 공개했으면 '공개하지 않은 값'에 넣지 않는다. 한 메시지에 최대 6줄이다.
- 일부만 공개하면 메시지 종류가 '일부 공개 승인'이다. 의료진 화면 API의 메시지에 `partial`이 붙고, 요청 상태는 '일부 승인'이 된다.
- 승인 메시지는 요청한 사례로 보낸다. 다른 사례의 값을 승인해도 그 요청의 상태가 바뀌게 하기 위해서다. 줄마다 사례 이름이 있다.
- 감사 기록 `approve_release`에 공개하지 않은 단서(`kept`)를 남긴다.

### 2. 승인한 값을 사례 카드에

- 승인한 진단 · 대표 항목(처방 약 · 시술 · 관리 계획)은 사례 목록 카드에 그 값으로 보인다(`apply_approval`이 카드 제목을 바꾼다).
- 카드에 '승인 공개 진단'처럼 승인한 단서를 표시한다(`/api/cases`의 `approved`).
- 공개 승인 메시지가 새로 오면 화면이 사례 목록과 그 사례 노트를 다시 받는다. 답을 받은 뒤에도 사례 목록을 다시 받는다(`refreshCases`). 로딩 표시는 하지 않는다.

### 3. 요청할 사례를 고른다

- **답 아래 요청 창**
  - 그 답에서 값이 바뀐 사례가 여럿이면 '요청할 사례' 칩에서 고른다.
  - 초안의 항목 이름은 고른 사례의 것으로 바뀐다. 의료진이 고친 초안은 그대로 둔다.
  - 요청 상태는 그 답의 사례들 가운데 마지막 요청으로 본다.
- **보호 담당자 창의 새 요청**
  - 사례 선택 칸이 생긴다.
  - 기본 사례는 창을 연 곳이 가리킨 사례다. 머리줄 알림이면 보호 담당자의 마지막 메시지 사례, 요청 상태 단추면 그 답의 사례, 미리 보기면 그 메시지 사례다. 그런 사례가 없으면 고른 사례다.

### 4. 열기 실패를 화면에 남긴다

- 외래 목록의 열기 단추 아래에 실패 칸을 두고, '다시 시도' · '닫기'를 붙인다. 다른 환자를 고르면 지운다(`lib/openFailure.ts`).
- 서버가 까닭을 보냈으면 그 까닭을 쓴다. 예: "대상 AI 호출에 실패했습니다 (LLMHTTPError). …"
- 앞단(프록시 · 터널)이 끊은 502 · 524 등 본문 없는 응답이면 "응답을 기다리다 연결이 끊겼습니다 (HTTP 502, 58초 지나서)"라고 쓴다. 이어서 "서버가 그 사이 답을 마쳤으면 다시 시도할 때 바로 열립니다"라고 안내한다.
  - 서버는 연결이 끊겨도 첫 답을 계속 만든다. 같은 환자 · 목적은 첫 답을 다시 쓰므로(ADR-0024), 다시 시도하면 빨리 열릴 수 있다.
- 5xx · 연결 실패 뒤에는 진료 중 환자 정보를 다시 받는다. 서버가 그 사이 환자를 열었을 수 있기 때문이다.

### 5. 기록에 없는 원인 · 목적을 짐작하지 않는다 (판정 규칙 v6)

- **대상 AI 답 형식**(`live.ANSWER_STYLE`): "처방 이유 · 치료 목적 · 진단처럼 기록에 적혀 있지 않은 것은 짐작해 쓰지 않습니다. 물었는데 기록에 없으면 '기록에 없음'이라고만 씁니다."
- **재작성기 지시**(`review.rewrite_rules` 10번): "원래 답에 없던 원인 · 목적 · 진단을 짐작해 덧붙이지 않는다. 값을 빼거나 범위로 바꾼 자리를 '…로 보입니다', '아마 …', '일반적으로 …'처럼 그럴듯한 설명으로 채우지 않는다." 다시 고칠 때의 '남은 표현' 안내는 11번이 된다.
- 판정 규칙 판을 `medicloak-release-v6`으로 올린다. 대상 AI 답이 달라지므로, 실제 LLM으로 켜면 자동 레드팀 점검이 한 번 돈다(ADR-0028). 답 형식 지시문 해시(`ANSWER_STYLE_ID`)도 바뀌어, 첫 답 나눠 쓰기 열쇠가 새로 생긴다.

### 6. 보내기 전 안내는 추정이라고 말한다

- 의료진 화면 API의 보내기 전 확인에 `estimate`(실제 LLM 대화면 `oracle`)를 남긴다. 숫자가 아니라 '미리 센 것'이라는 표시다. 왜 그렇게 답하는지를 `basis`로 함께 준다: `count` 후보 수 · `rule` 보안 담당자 규칙 · `purpose` 조회 목적.
- 실제 LLM 대화에서 후보 수로 정한 안내는 이렇게 쓴다: "미리 세어 보면 사례 5의 처방 약은 비공개로 표시될 수 있습니다. 실제로 바꿀 값은 AI 답을 받은 뒤 다시 정합니다."
  - 경고가 없으면 "미리 세어 보면 그대로 답할 수 있는 질문입니다"라고 쓴다.
- 규칙 · 조회 목적으로 가리는 것은 답이 어떻든 확정이라, 지금처럼 확정 문장이다. 결정적 응답기 데모의 문구도 그대로다.

**결과와 영향**

- 판정 규칙 판이 v6이다. 실제 LLM으로 서버를 켜면 '유형마다 1명' 레드팀(어림 540번 호출)이 한 번 돈다. `--auto-redteam off`로 미룰 수 있다.

  - 의료진 메시지의 `partial`, 사례 목록의 `approved`

  - 감사 기록 `approve_release`의 `kept`

모두 의료진 대화(운영 모드, 실제 LLM)에 건다. 연구 모듈(`medical/`)과 고정본(`normalize_bridge`)은 바꾸지 않는다. 레드팀은 공개 직전 문장 처리(아래 3)만 같이 받는다. 라이브러리(`Engine`)의 기본값은 끔이라 지금까지의 데모 · 테스트 동작은 그대로이고, `python -m medicloak serve`는 기본으로 켠다.

### 1. 과거 환자 단위 공개 원장 (검토 P0-1, `ledger.py`)

- 화면 갈래(C1) State에 새로 들어간 값(턴마다)과 승인 공개한 값을 과거 환자 번호로 적는다. DB 표 `disclosure_ledger`(과거 환자 · 대화 · 계정 · 시각 · 종류 · 턴 · 단서 · 노드 · 사건 표지)에 남기고, 서버를 켤 때 기간 창 안의 기록을 다시 읽는다.
- 판정 기준은 '이 사례의 State + 다른 대화에서 같은 과거 환자에 대해 나간 값(최근 90일)'이다. 다른 대화의 값은 대화마다 사건 묶음을 따로 둔다(`사례N:대화:사건`). 출력 단계(공개 판정 · 다시 확인), 입력 게이팅, 공개 승인의 '공개 뒤 후보 수', 공개 미리 보기, 의료진 화면의 판정 상태가 모두 이 기준을 쓴다.
- 관제: 이 대화에서 값이 나간 사례가 다른 대화와 합치면 기준 아래이면 `global_low`로 표시하고 확인 필요에 넣는다(깃발 '다른 대화와 합치면 기준 아래', 개요 집계). 가리기만 한 사례는 넣지 않는다. 그 사례가 낮은 것은 값을 낸 다른 대화의 위험이기 때문이다.
- 관제 상세에는 사례마다 다른 대화에서 나간 값 수 · 대화 수 · 계정 수 · 승인 수와 합친 후보 수(`ledger`)가 있고, '후보가 줄어든 과정' 맨 앞에 '다른 대화에서 공개된 값' 단계가 보인다. 값 자체는 보이지 않는다.
- 의료진 화면에는 숫자 없이 '이 사례는 다른 진료 대화에서 이미 공개된 정보까지 합쳐 판단했습니다'만 덧붙인다.

### 2. 대상 AI 입력 게이팅 (P0-2, `gate.py`)

- 대상 AI를 부르기 전에 사례 문서의 사실 줄마다 그 사례의 지금 State(원장 포함)로 판정한다. 순서는 출력 단계 Defender와 같다.
  - 그 값 하나를 더해도 후보가 5명보다 많으면 그대로 둔다.
  - 원래 값으로 3명 이하면 가린다.
  - 그 사이면 후보가 기준을 넘는 가장 가까운 상위 범주로 넓힌다.
  - 조회 목적에 필요 없는 단서(거주 지역)와 보안 담당자 규칙은 가린다. 나이 · 날짜는 최소 공개 단위(5세 · 월)로, 민감 값은 아래 4의 기준으로 판정한다.
- 가린 값은 '(비공개)', 넓힌 값은 상위 범주 이름으로 바꿔 넣는다. 횟수 줄은 범위로 바꾼다('총 7회' → '총 4~9회'). 날짜를 가리거나 넓힌 항목은 끝 날짜 줄에 기간 범위를 남긴다('(시작부터 약 1~2주)', 검토 P2-2). 지시문 사례 블록 머리에 '가리거나 넓힌 값은 짐작해 채우지 말라'는 한 줄을 넣는다.
- 첫 답(턴 0)은 열 때와 미리 준비 모두 같은 게이팅 요청을 만든다(`Engine.clinic_prefix`, 원장은 읽기만 한다). 첫 답 나눠 쓰기는 요청의 SHA-256으로 찾으므로, 원장이 바뀌면 새 요청이 된다. 다음 질문부터는 턴마다 그때 State로 다시 게이팅한다(`RuledArmRun._turn`).
- 후보 수는 '그 사례 State의 후보 집합 ∩ 그 값을 가진 환자'로 센다. 새 값은 자기만의 사건 묶음이라 kcalc가 그 값 하나를 더해 센 k와 같다(898건 대조에서 차이 0, 테스트로 고정). 교집합이 0이면 kcalc로 다시 센다.
- 값 하나씩 판정한다. 여러 값을 함께 말해 후보가 줄어드는 위험은 지금처럼 출력 단계가 막는다.

### 3. 공개 직전 문장 처리 (P0-3 · P1-4 일부, `textguard.post_release`)

실제 LLM 방어 갈래(C1 · C1S)의 내보낼 글에, 사례를 가리키는 문장에만 순서대로 건다.

- 기간 · 간격 · 횟수는 정해 둔 범위로 바꾼다('약 12일' → '약 1~2주', '3개월 간격' → '1~3개월 간격', '총 7회' → '총 4~9회'). '하루 2회' 같은 복용 빈도는 그대로 둔다.
- 부재 · 배타 진술:
  - '그 외 · 다른 … 없음'은 그 말을 뺀다.
  - 'X 외에는 … 없음'은 'X … 기록이 있음'으로 바꾼다.
  - '…만'은 앞말에 맞는 조사로 바꾼다('acetaminophen만 처방받았고' → 'acetaminophen을 처방받았고').
  - 다른 말 없이 '… 없습니다'만 말하는 문장('사례1 기록에는 처방 약이 없습니다')은 문장째 뺀다. 게이팅된 '(비공개)'를 대상 AI가 없다고 잘못 읽은 것일 수 있고, 맞더라도 후보 수 계산에 없는 부정 정보다.
- 기록에 없는 원인 · 목적 짐작('…때문으로 보입니다', '아마')은 짐작 부분을 떼고, 남는 말이 없으면 문장째 뺀다.
- 답이 통째로 비면 '질문하신 내용 가운데 기록으로 확인할 수 없는 부분은 답에서 뺐습니다.' 한 줄을 보낸다.
- 사례 문서로 설명되지 않는 영문 용어는 기록만 한다(최대 20개). 문서 대조에 괄호 안 상품명과 제형 이름을 더했다.
- 바꾼 내용은 턴 기록 `post_edits`에 남고, 관제 화면은 열람 전에 뺀 문장을 지운다. 의료진 화면 설명에는 한 줄씩 덧붙인다.
- 레드팀 실제 LLM 갈래에도 걸리므로 판정 규칙 판을 v7로 올린다.

### 4. 민감도 등급 (P2-3, `sensitivity.py`)

- 등급 2(엄격):
  - 물질 사용: F10-F19
  - 정신 건강: ICD 5장
  - 생식 · 피임 · 임신: 15장, Z30-Z39, 피임약 ATC G03A · G02B, 시술 · 계획 이름
  - HIV · 성매개 감염: B20, Z21, A50-A64, 항레트로바이러스 ATC J05A 계열
- 등급 1: 암(2장). 표시만 하고 기준은 그대로다.
- 약 이름으로 진단을 거꾸로 알 수 있는 경우(Mirena, buprenorphine · naloxone, 항정신병약, 항우울제 등)는 ATC 상위 범주와 성분 · 상품명으로 잡는다.
- 등급 2 값은 내보낸 뒤 후보가 `--strict-k`(기본 10)명 이상일 때만 낸다. 아니면 민감하지 않은 상위 범주 가운데 후보가 그만큼 되는 가장 가까운 것으로 넓히고, 없으면 가린다. 입력 게이팅과 출력 단계(`RuleDefender`)가 같은 규칙을 쓴다. 예를 들어 치매 진단(F02, 후보 9명)은 보통 기준으로는 그대로지만, 상위 범주가 모두 5장이라 가린다. 피임 패치(후보 9명)는 ATC G03으로 넓힌다.
- 미성년 시기(19세 미만) 물질 사용 장애 진단이 있는 과거 환자는 유사 사례 검색에서 뺀다. 후보 수의 기준 집단에서는 빼지 않는다. 이 합성 데이터에는 해당 환자가 없다.
- 관제 상세의 검색된 사례에는 열람 전에 '민감 기록 있음'만, 열람 뒤에 범주 이름을 보인다.

### 5. 답 시간 한도 (P1-5)

- 질문을 받은 때부터 `--answer-budget`(기본 45초)을 넘기면, 재작성기를 부르기 전이나 다시 확인하기 전에 멈추고 거절 문장을 보낸다(공개 방식 `REFUSAL_TIMEOUT`). State와 원장에는 아무것도 더하지 않는다.
- 이미 보낸 LLM 요청 하나는 끊지 않는다(요청마다의 제한은 `LLM_TIMEOUT_SEC`).
- 의료진 화면은 '정해진 시간 안에 답을 확인하지 못해 보내지 않았습니다. 잠시 뒤 다시 물어보세요.'라고 알린다.

### 6. 미리 확인 한도 (P1-3 일부)

- 의료진 '보내기 전 확인'은 대화마다 10분에 20번까지다. 넘으면 판정 없이 `limited`만 돌려주고(화면: '보내기 전 확인을 잠시 멈췄습니다. 보내면 서버가 확인합니다'), 감사 기록 '보내기 전 확인 한도 넘음'을 한도마다 한 번 남긴다. 보낸 질문의 서버 판정은 그대로다.
- 보안 담당자 '질문 미리 세기'는 후보 수를 그대로 보여 주는 도구다. 부를 때마다 감사 기록 '보안 담당자 질문 미리 세기'(사례 · 질문 글자 수, 본문 없음)를 남기고, 계정마다 10분에 30번까지다(넘으면 429).
- 2인 승인과 '특정 시도 막음' 이름은 앞서 정한 대로 바꾸지 않는다.

### 서버 옵션

`--ledger on|off`, `--ledger-window-days 90`(0이면 기간 없이 모두), `--input-gate on|off`, `--answer-budget 45`(0이면 끔), `--sensitivity on|off`, `--strict-k 10`. 켤 때 보강 상태를 한 줄로 찍고, 보호 정책 화면(`/api/monitor/policy`의 `protections`)에 보인다.

**결과와 영향**

- 판정 규칙 판이 v7이다. 실제 LLM으로 서버를 켜면 '유형마다 1명' 레드팀(어림 540번 호출)이 한 번 돈다. `--auto-redteam off`로 미룰 수 있다.
- 비교 갈래의 뜻이 바뀐다. 세 갈래는 같은 원 응답을 쓰는데, 게이팅을 켜면 그 원 응답이 게이팅된 지시문으로 받은 답이다. 그래서 '방어 없음(C0)'은 '출력 단계 방어 없음'이 되고, C0의 후보 수는 게이팅 전보다 높게 나온다. 게이팅 전 기록과 견줄 때 주의한다.
- 레드팀은 원장 · 게이팅 · 민감도 기준을 쓰지 않는다(문장 처리만). 레드팀으로 잰 방어 효과는 출력 단계 방어의 값이다.
- 대상 AI가 보는 정확한 날짜가 크게 준다. 예를 들어 T0014 첫 답에서 사례1 값 48개 가운데 그대로 16 · 넓힘 10 · 가림 22였고, 가린 값은 대부분 날짜다. 기간은 범위로 남는다. 답 품질은 실제 LLM으로 확인해야 한다.
- 게이팅 계산은 처음 사례 5건에 0.7초쯤 걸리고, 값마다 가진 환자 집합을 한 번 만든 뒤에는 짧다.
- DB에 `disclosure_ledger` 표가 생긴다(`CREATE TABLE IF NOT EXISTS`라 예전 DB도 그대로 켜진다).
- API에 더해진 것:
  - 관제 목록 · 개요: `global_low`, `k_global`, 집계 `global_low`
  - 관제 상세: `ledger`, 검색된 사례 `sensitive`, `gated`. 턴마다 `input_gate`(사례별 그대로 · 넓힘 · 가림 수), `post_edits`, 사례 `k_global`
  - 후보가 줄어든 과정: 원장 단계 `prior: true`
  - 보내기 전 확인: `limited`
  - 공개 방식: `REFUSAL_TIMEOUT`
  - 감사 기록: `watch_preflight`, `preflight_limited`
  - 보호 정책: `protections`
- 화면: 보호 정책에 보강 네 줄, 관제 개요 문장 · 집계와 목록 줄에 '다른 대화와 합치면 기준 아래', 후보가 줄어든 과정 맨 앞에 '다른 대화' 단계, 의료진 화면의 시간 초과 · 미리 확인 한도 문구, 감사 기록 글.
- 테스트: `tests/medicloak/test_review_hardening.py` 13개(원장의 기간 창 · 다시 켜기 · 세 의사 결합과 관제 표시, 첫 답 · 다음 질문 게이팅, 게이팅 후보 수와 kcalc 대조, 문서 렌더링, 민감도 입력 · 출력 단계, 미성년 물질 사용 제외, 문장 처리, 시간 초과, 미리 확인 한도, 서버 옵션 기본값, 보호 정책). 화면 테스트 5개를 더했다.

### ADR-0033. RAG 기준 재측정 도구(요청서 R2~R6)를 연구 모듈 밖에 두고, 원본 대조로 찾은 날짜 누락을 추출 바로잡기에서 고친다

- 승인 · 2026-11-06 · 결정 양승준 · S5 · 실험·검증
- 근거: `scripts/rag_common.py`, `scripts/rag_retrieval_dump.py`, `scripts/rag_remeasure.py`, `scripts/rag_postcalc.py`, `scripts/rag_truth_verifier.py`, `webdemo/backend/textguard.py`, `webdemo/backend/review.py`, `tests/test_rag_remeasure.py`, `tests/medicloak/test_review_hardening.py`, `docs/rag_remeasure/README.md`

**결정**

### 1. 재측정 도구는 `scripts/`에 둔다 (연구 모듈 · 고정본은 바꾸지 않는다)

- `rag_retrieval_dump.py` (R2, LLM 0)
  - 질의 후보 115명 × 조회 유형 3을 검색만 한다. 실행(make_prefix)과 같은 검색이다.
  - 노출 분포와 기준 희귀도를 센다. 기준 희귀도는 원본 단서 몇 개면 후보가 5명 아래가 되는지의 최솟값이고, 의료 항목 기준과 모든 단서 기준 두 가지로 센다.

- `rag_remeasure.py` (R3 · R4 · R6)
  - 결과 ⑥과 같은 경로(make_prefix → RuledArmRun(live=True))로 돈다. 다만 서버와 같은 `LiveLLM` 추출 바로잡기를 거친다.

  - 질문 계획을 정한다. 기본 `F,P,P,S,D,D,D`는 퍼저 하나, 같은 질문을 다른 표현으로 둘, 범위 전환 하나, 파생 값 셋(며칠 만에 · 몇 번 · 그 약만)이다.

  - 턴마다 검색된 5명 전원의 저장소 환자 ID · 공개 단서 · 시스템 k를 남긴다.
  - R6는 R4 기록의 C1 · 반복 0 질문 7개를 대화 1 · 2 · 4 · 7개로 나눠 다시 묻는다. C1G(C1 + ADR-0032 공개 원장)를 같은 조건으로 함께 돌린다.

- `rag_truth_verifier.py` (R5): 제품 추출기 · 정규화기와 독립인 닫힌 집합 매칭으로 진짜 k를 센다. 숨은 위반, 단서 종류별 재현율, 사람 검수 시트를 낸다.

### 2. 정의

- 위반은 1 ≤ k < 5다. 0건이면 단측 95% 상한(1 − 0.05^(1/n))을 같이 적는다.
- 대화 간 합산의 사건 묶음
  - 결정적 응답기는 원본 사건 표지('e_…')를 쓰므로 환자 단위로 합친다.
  - 실제 LLM 추출은 'e1' 같은 대화 안 번호를 쓰므로 대화마다 따로 둔다. 다른 대화의 'e1'은 다른 사건일 수 있다.
- 진짜 k의 사건 묶음은 같은 문장에서 같은 원본 사건으로 매칭된 값만 잇는다. 공격자가 답에서 이어 볼 수 있는 만큼이다.
- 기간 · 횟수 · 부재 진술은 진짜 k에 넣지 않는다. 따로 세고 재현율 0으로 적는다.

### 3. 날짜 값 바로잡기 (제품, `textguard.fix_period_value`, 판정 규칙 v8)

추출기 출력을 공개 판정에 넘기기 전에 날짜 단서의 값을 정규화기가 읽는 꼴(2017-11-20 · 2017-11 · 2017)로 바꾼다.

- 값에 날짜가 없고 근거 문장에 날짜가 하나만 있으면 그 날짜를 값으로 쓴다.
- '2014년 4월 1일' · '2014.04.01' 꼴은 ISO 꼴로 바꾼다.
- 날짜가 둘 이상이면 그대로 둔다.

원 답 추출과 재작성 뒤 다시 확인 추출에 모두 걸린다. 의료진 대화, 실제 LLM 레드팀, `rag_remeasure.py`가 같은 경로다. 결과 ⑥ 기록 T0003 턴 4를 다시 넣어 보면 사례1의 k가 346에서 1로 잡혀 판정이 날짜를 가린다.

**결과와 영향**

- 결과 ⑥ 실제 LLM 6명의 C1 '위반 0/6'은 시스템 추출 기준 값이다. 원본 대조로는 2/6이었다.
- R4는 이 커밋(판정 규칙 v8, 추출 바로잡기 포함)에서 돌려야 고친 뒤의 제품을 잰다.
- 판정 규칙 판이 v8이라 실제 LLM으로 서버를 켜면 자동 레드팀 점검이 한 번 돈다.
- 테스트
  - `tests/test_rag_remeasure.py`: 가짜 HTTP 위 실제 LLM 경로로 R2 → R4 → 사후 계산 → 원본 대조 → R6를 끝까지 한 번 돈다.
  - `tests/medicloak/test_review_hardening.py`: 날짜 값 바로잡기.

### ADR-0034. 의료진은 담당 외래 환자만 열고, 담당이 아닌 환자는 사유를 적은 예외 열람으로만 연다 (EMR 접근 관리)

- 승인 · 2026-11-07 · 결정 양승준 · S5 · 시스템·화면
- 근거: `webdemo/backend/access.py`, `webdemo/backend/app.py`, `webdemo/backend/fhir.py`, `webdemo/backend/emr.py`, `webdemo/backend/store.py`, `webdemo/backend/monitor.py`, `medicloak/cli.py`, `frontend/src/pages/EmrPage.tsx`, `frontend/src/pages/EmrAccessPage.tsx`, `frontend/src/components/clinic/PatientBanner.tsx`, `tests/medicloak/test_assignment.py`, `tests/medicloak/test_medicloak.py`, `medicloak/README.md`

**결정**

### 1. 담당 배정 (`webdemo/backend/access.py`)

- 외래 환자(QUERY_POOL 115명)마다 담당 의료진을 둔다 (`emr_assignment`). 한 환자에 여러 명을 둘 수 있다.
- 처음에는 규칙으로 나눈다. 환자 번호 순서대로, 지금 담당 환자가 가장 적은 의료진 계정에 하나씩 준다 (같으면 먼저 만든 계정). 처음 계정 둘이면 58명 · 57명이다.
- `init`과 서버를 켤 때, 담당이 없는 외래 환자만 같은 규칙으로 채운다. 이미 담당이 있는 환자는 옮기지 않는다.
- 바꾸기는 명령으로만 한다: `python -m medicloak assign [list | add <번호> <아이디> | remove <번호> <아이디> | auto [--reset]]`. 바꾼 일은 감사 기록(`emr_assign`)에 남고, 환자는 번호 대신 기호로 남는다.

### 2. 의료진은 담당 환자만 연다

- `/api/emr/worklist`는 로그인한 의료진의 담당 환자와 예외 열람 중인 환자만 돌려준다. 줄마다 `access`(assigned · break_glass)가 붙는다.
- 같은 검사를 차트 요약(`/api/emr/chart`, 새로 만듦) · 오늘 볼 진단(`/api/emr/visits`) · 진료 지원 AI 열기(`/api/emr/launch`) · 첫 답 미리 준비(`/api/emr/prefetch`) · FHIR(`/fhir/Patient`, `/fhir/{자원}?patient=`)에 건다.
- 외래 환자가 아니면 지금처럼 404다. 외래 환자인데 담당이 아니면 403이다 (머리글 `X-MediCloak-State: not-assigned`, FHIR는 OperationOutcome `forbidden`).
- 거부는 접근 기록과 감사 기록(`emr_denied`)에 남긴다. 같은 의료진 · 환자 · 요청의 거부를 60초 안에 또 받으면 한 번으로 센다.
- 진료 지원 AI 목적(연구 계획의 trial)이 없는 외래 환자 1명도 목록에 넣는다. 목적 없이 차트만 볼 수 있다.

### 3. 담당 외 환자 열기 (예외 열람, break-glass)

- 환자 번호(앞 8자리) · 사유 분류(협진 · 당직/응급 · 기타) · 직접 쓴 설명(5자 이상)을 모두 적어야 열린다. 미리 골라 둔 사유는 없다 (ADR-0030과 같은 규칙).
- 연 뒤 12시간 동안 담당 환자처럼 목록 · 차트 · 진료 지원 AI를 쓴다. FHIR Patient의 생년 · 거주 지역은 빼고 보인다.
- 연 일은 감사 기록(`break_glass`)과 접근 기록에 남고, 보안 담당자 EMR 접근 화면에 '검토 대기'로 올라온다.
- 검토는 두 가지다: 적절함(`ok`)과 확인 필요(`flag`). 확인 필요는 까닭을 적어야 하고, 열람을 바로 끝낸다. 검토도 감사 기록(`break_glass_review`)에 남는다.
- 같은 환자를 이미 열어 두었으면 새로 만들지 않는다. 담당 환자를 예외 열람으로 열려고 하면 409다.
- `serve --break-glass off`면 새로 열 수 없고, 열어 둔 것도 쓰지 않는다 (담당 환자만).

### 4. 접근 기록 (`emr_access`)

- 다음을 환자마다 남긴다: 차트 열람(1분 안에 다시 열면 한 번), EMR 연동(FHIR) 조회(10분에 한 번), 진료 지원 AI 열기, 거부, 예외 열람, 보안 담당자 차트 열람.
- 감사 기록에는 보안에 중요한 일(거부 · 예외 열람 · 검토 · 보안 담당자 열람 · 배정 변경)만 같이 남긴다.

### 5. 보안 담당자 EMR 접근 화면 (`/emr-access`)

- 외래 환자마다 기호(P-xxxxxx) · 진료 상태 · 담당 · 마지막 접근 · 7일 접근 수 · 예외 열람 수만 보인다 (`GET /api/monitor/emr`). 진단 · 나이 · 성별 · 환자 번호는 보내지 않는다.
- 차트는 사유(분류 + 5자 이상 설명)를 적어야 열린다 (`POST /api/monitor/emr/patients/{기호}/reveal`). 그때 환자 번호와 차트 요약이 보이고, 감사 기록(`emr_reveal`)에 남는다. 의료진 대화 원문 열람(ADR-0030)과 같은 규칙이다.
- 환자 기호의 열쇠와 식은 관제 화면 · 감사 기록과 같다 (`access.subject_tag`). 명령줄도 같은 열쇠를 쓴다.
- 배정은 이 화면에서 보기만 한다.

### 6. 의료진 화면 흐름

- 로그인하면 '내 담당 환자'(`/emr`)가 열린다. 왼쪽 목록(상태 탭 · 찾기 · 담당 외 환자 열기) → 가운데 차트 요약(진단 이력 · 처방 · 시술 · 관리 계획 · 최근 내원 · 내원 흐름) → 오른쪽 '유사 사례 찾기' 순서다. 유사 사례 찾기는 진료 목적 · 오늘 볼 진단 · 첫 답 미리 준비 · 열기를 지금까지와 같이 한다.
- 환자를 고르면 주소가 `/emr/{환자 id}`로 바뀐다. 좁은 화면에서는 목록과 차트를 한 화면씩 보인다.
- 위 환자 띠는 '지금 보는 환자'로 이름을 바꾼다. 운영 모드에서는 진료 지원 AI 대화가 열려 있을 때만 보이고, 내 담당 환자 화면에서는 숨긴다. 띠의 '차트'를 누르면 그 환자의 차트로 돌아간다.
- 데모 모드(`python -m webdemo`, 로그인 · EMR 없음)는 띠 이름 말고는 바꾸지 않는다.

**결과와 영향**

- DB에 표 셋이 늘었다: `emr_assignment` · `emr_grant` · `emr_access`. `CREATE TABLE IF NOT EXISTS`라 기존 DB를 열면 그대로 붙고, 서버를 켤 때 담당을 채운다.
- 검사는 여는 때 한다. 담당이 바뀌어도 이미 열린 진료 지원 AI 대화는 이어진다.
- 새로 만든 의료진 계정은 담당이 없다. 운영자가 `assign add` 또는 `assign auto --reset`으로 준다.
- 테스트: `tests/medicloak/test_assignment.py` 8건(규칙 · 번호 찾기 · 예외 열람 · 접근 기록 · 기호 · 차트 요약 · 명령). `tests/medicloak/test_medicloak.py`에 담당 · 예외 열람 · 보안 담당자 화면 흐름 1건을 더했다. 기존 테스트의 열기 도우미는 그 환자를 담당으로 먼저 더한다. 앞단 vitest에 감사 기록 글과 남은 시간 표시를 더했다.
- 연구 하네스(`medical/`) · 고정본(`medical/bundle/`)은 바꾸지 않았다.

**ADR-0030**

- 의료진 쪽: 요청 결과를 항목마다 알리기, 승인한 값을 사례 카드에 반영, 요청 양식에서 사례 고르기, 열기 실패 오류 칸과 다시 시도, 추측하지 말라는 지시(판정 규칙 v6), 보내기 전 확인 문구.

- 고위험 승인을 모아 보는 정기 점검(리포트에 목록).
- 대화 사이 누적을 판정에 넣을지 연구한다.

**ADR-0031**

- 요청함: 대기 · 승인 · 반려와 처리 기한을 두고, 서버를 다시 켜도 답하지 못한 요청이 이어지게 하기(체험 기록에서 지난 대화의 요청이 '답하지 못한 요청'으로 남았다).
- 열기의 시간 상한: 다시 확인이 길어지면 보수적으로 가린 답을 내는 fail-safe.
- 짐작 문장이 실제로 줄었는지 실제 LLM 레드팀 · 체험으로 확인한다.
- 사례 카드의 '세부 정보 제한' 문구를 승인 뒤에도 그대로 둘지 정한다.

**ADR-0032**
